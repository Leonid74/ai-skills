# leonid74-ai-skills — маркетплейс плагинов для Claude Code

Каталог плагинов для Claude Code. Доступные плагины:

- **andrej-karpathy-skills** — поведенческие принципы Андрея Карпатого для
  уменьшения типичных ошибок LLM при написании кода *(внешний плагин,
  автор: forrestchang)*.

- **chat-handoff** — переносит контекст текущего диалога в новый чат одним
  готовым markdown-блоком *(миграция сессии, не суммаризация)*.

- **dev-toolkit** — инструменты повседневной разработки на PHP/Go/JS:
  - *Slash-команды:* `/dev-toolkit:review-quick`, `/dev-toolkit:review-last`,
    `/dev-toolkit:pr`, `/dev-toolkit:cppr` — code review и подготовка PR
  - *Skills:* `review-code` — многоуровневое ревью диффа (`low`…`max`; `low` —
    безагентный проход, `medium`+ — параллельный поиск с adversarial-верификацией);
    `todo-ship` — сквозное закрытие пункта TODO (реализация → ревью → PR → мёрж → релиз →
    проверка результата);
    `statusline-setup` — настройка строки статуса Claude Code (папка, модель и effort, заполнение контекста, расход лимитов подписки за пять часов и за неделю, ветка; внутри tmux — процент контекста в опции панели `@claude_ctx`);
    `optimize-project-docs` — оптимизация и реконсиляция `CLAUDE.md` / `README` / памяти проекта;
    `server-disk-cleanup` — анализ места на диске Linux-сервера и очистка только выбранных пунктов;
    `debug` — систематическая отладка: сначала корневая причина, потом одна проверенная правка
  - *Хук защиты:* блокирует деструктивные Bash-команды (`rm -rf`,
    `git reset --hard`, `git push --force`, `git branch -D`, чтение `.env`,
    вывод окружения) и случайную передачу значений секретов/токенов
  - *Хук напоминания:* после компакции контекста просит перечитать рабочие файлы
    `PLAN-*.md` / `HANDOFF*.md` из `.dev/` и `.dev_files/`
  - *Хук уведомлений:* звуковой сигнал, когда Claude ждёт ответа или
    завершил работу

## Установка

Выполни в Claude Code:

```bash
/plugin marketplace add https://github.com/Leonid74/ai-skills
/plugin install chat-handoff@leonid74-ai-skills
/plugin install dev-toolkit@leonid74-ai-skills
/plugin install andrej-karpathy-skills@leonid74-ai-skills
```

Или, после подключения маркетплейса, выбери плагины интерактивно:

```bash
/plugins
```

Срабатывает по описанию — направляет работу Claude согласно принципам
Андрея Карпатого: думать перед кодированием, минимальные изменения,
простота, чёткие критерии успеха.

### dev-toolkit

#### Slash-команды

| Команда                     | Что делает                                        |
|-----------------------------|---------------------------------------------------|
| `/dev-toolkit:review-quick` | Быстрое code review изменённых файлов (git diff)  |
| `/dev-toolkit:review-last`  | Code review последнего коммита                    |
| `/dev-toolkit:pr`           | Подготовка Pull Request                           |
| `/dev-toolkit:cppr [файл]`  | Коммит, пуш и создание PR одной командой          |

С 1.19.0 `/dev-toolkit:cppr` создаёт PR только через `gh pr create --body-file` и принимает
необязательный аргумент — путь к готовому файлу описания PR (например, с метаданными ревью от
вызывающего флоу). Готовый файл используется как есть и сверяется с требованиями проекта к
описанию PR ещё до коммита и пуша. **`/dev-toolkit:pr` проектные хуки-гейты не поддерживает**
(описание передаёт не файлом): в проектах, где хук требует `--body-file` или метаданных ревью в
описании PR, используйте `/dev-toolkit:cppr`.

> ⚠️ С версии `1.11.0` команда `/dev-toolkit:review` переименована в
> `/dev-toolkit:review-quick` — старое имя не работает. Глубокое ревью с уровнями
> живёт в скилле `review-code` (ниже).

#### Skill: review-code

Многоуровневое code review диффа: калибровка глубины по уровню (`low` —
безагентный однопроходный режим; `medium`…`max` — 3–9 независимых углов
поиска с каталогами классов багов), adversarial-верификация выживших кандидатов
(precision-скептик на `medium`, recall-протокол `CONFIRMED`/`PLAUSIBLE`/`REFUTED`
на `high`+, три разные линзы на `max`), sweep-фаза поиска пропусков на
`xhigh`/`max` и типизированный вывод находок в UI.

Вызов вручную: `/dev-toolkit:review-code <уровень> [target] [pass=N]`, где `target` — пусто
(рабочий дифф), `<base>...<head>` (напр. `master...HEAD`) или номер PR, а `pass=N` — номер
прохода конвейера ревью проекта (по умолчанию 1). Skill
также вызывается самой моделью — этим он отличается от встроенного
`/code-review`, который с версии CLI 2.1.215 запускает только пользователь (зато
у встроенного есть облачный режим `ultra`, которого здесь нет и который
воспроизводить не нужно).

Отличие от `/dev-toolkit:review-quick` и `/dev-toolkit:review-last`: те — быстрый
однопроходный обзор без уровней и верификации. Правила ревью (security-поверхность,
контракты, конвенции) skill вычитывает из `doc/REVIEW.md` (или `REVIEW.md` в корне) и
`CLAUDE.md` целевого проекта, а при их отсутствии применяет дефолтную эвристику и явно об
этом сообщает. Это самостоятельный инструмент, а не эмуляция встроенного `/code-review`.

**Файл правил ревью `doc/REVIEW.md`** (с 1.19.0) — позволяет держать правила ревью отдельно от
разросшегося `CLAUDE.md`. Приоритет — по темам: то, что файл ревью задаёт, перекрывает `CLAUDE.md`,
остальное по-прежнему берётся из `CLAUDE.md`. Распознаются заголовки, **точно** равные имени
секции (жирный пункт списка заголовком не считается):

| Секция | Что в неё класть |
|---|---|
| `Уровни и зоны` | пороги уровней, перечень security-поверхности и контрактов (уровень `max`), перечень зон ядра (`xhigh`) |
| `Не репортить` | skip-list — классы находок, которые не репортятся; security-находки не подавляются никогда, пункты, сужающие scope («не анализировать X»), не применяются |
| `Нормы проходов` | уровень и scope проходов 2 и далее (номер прохода — аргумент `pass=N`); ниже `max` для security и `xhigh` для зон ядра не опускают; scope — только форма (по range правок или полный), исключение путей — пункт, сужающий scope, и не применяется |
| `Верификационная планка` | требования к доказательству вердиктов — только ужесточают протокол, не отменяют верификацию |

Прочие секции — обычные правила проекта. Файл ревью, изменённый в самом ревьюируемом диффе, этот
дифф не судит: его skip-list, верификационная планка и понижающие уровень правила в таком прогоне
не применяются. Точная механика — раздел «Правила ревью проекта» в `skills/review-code/SKILL.md`.

**Правила проекта в брифе агентов** (с 2.1.0) — корневой `CLAUDE.md` агент получает от среды сам,
поэтому в бриф идут ссылки на применимые правила, а не копия текста; дословно — только то, чего у
агента нет: секции файла ревью, вложенные `CLAUDE.md`, пункты skip-list. Изменённый в диффе файл
правил (определение — фаза 0, п. 3 `SKILL.md`) защиты «не судит сам себя» пока не имеет — skill
называет такую правку в заголовке вывода и в «заметках» сводки для ручной проверки.

**Модель субагентов** (с 1.20.0) — зависит от роли, номера прохода и, с 2.8.0, модели сессии:
finder-углы (кроме security) и sweep идут на `opus` при `pass=1` и на `sonnet` при `pass` ≥ 2;
security-угол, верификаторы и линзы `max` — без параметра `model` (модель по умолчанию для субагентов
среды). С 1.21.0 skill уведомляет в заголовке вывода о цене правила (`sonnet` на повторных проходах,
в том числе на `max`; проект не может это отменить), а при втором отказе одного и того же угла
выносит решение пользователю с вариантами. С 2.8.0, если сессия идёт на `sonnet` или `haiku`
либо её модель неизвестна (в том числе название вне семейств `opus`/`sonnet`/`haiku`), security-угол, верификаторы на любом уровне (включая `xhigh`) и линзы
`max` получают `model: opus`, и уведомление заголовка называет это (в 1.21.0–2.7.0 оно только
предупреждало, что эти роли могут пойти на модели слабее). Правило смотрит на модель сессии: модель
по умолчанию для субагентов, заданную в среде слабее модели сессии, оно не видит. Если на повторном
проходе агенты на `opus` не ответили, а остальные ответили, skill рядом со штатными вариантами
предлагает пользователю ещё один — довести прогон без пола (с явной строкой об этом); сам он пол не
снимает.

**Оркестрация через `Workflow`** (с 2.0.0) — на `medium` и выше поиск, верификацию и sweep ведёт
workflow-скрипт плагина `workflows/review-code.js` (`dev-toolkit:review-code-pipeline`): результаты
агентов остаются в переменных скрипта, в сессию возвращается один итоговый объект, прерванный
прогон возобновляется с кэшем завершившихся агентов. Режим включается, только когда skill вызвал
сам пользователь **slash-командой** (или прямо попросил workflow) и оценка числа агентов
укладывается в ориентир «Dynamic workflow size» (`/config`); формула и числа оценки — в разделе
«Оркестрация фаз 1–2.5» `SKILL.md` (здесь не дублируются). Оценка выше ориентира — skill
останавливается и предлагает поднять ориентир, идти прежним режимом или запустить `Workflow` как
есть. При просьбе о ревью обычными словами, автономном вызове моделью (`todo-ship`, проектные флоу),
в headless-запуске и при недоступном или отклонённом `Workflow` работает прежний режим — вызовы
`Agent`; причина называется в заголовке и в поле «оркестрация» сводки.

**Темп запуска — волны по 5** (оба режима): агенты не запускаются залпом — волна из пяти, ответы
в журнал, затем следующая; первыми идут security и корректность. Ошибка лимита использования
(HTTP 429) — не «отказ агента»: перезапуск на неё не тратится, запуск останавливается, после сброса
лимита прогон продолжается с недостающих агентов. На `xhigh`/`max` skill заранее называет оценку
числа агентов и расхода. Разрешение на запуск `Workflow` skill сам себе не выдаёт
(`allowed-tools` его не содержит) — диалог разрешения остаётся гейтом.

После `ReportFindings` skill печатает сводку прогона (уровень, target, размер диффа, проход и
предупреждения, режим, оркестрация, агенты с разбивкой по моделям, минуты, токены или подсказка
ввести `/cost`, заметки, источник правил, подавленное skip-list) — её переносят в описание PR. В режиме
`Workflow` токены — общая сумма из уведомления о завершении workflow; разбивка по моделям
недоступна (только в `/workflows`).

> ⚠️ Плагинные артефакты всегда неймспейснуты — «голого» `/review-code` не будет,
> только `/dev-toolkit:review-code`.

#### Skill: todo-ship

Сквозное закрытие пункта списка задач: реализация в отдельной ветке → многоугловое ревью через
`review-code` → правки со сверкой всех затронутых файлов → PR и проверки проекта → мёрж → релиз →
проверка результата у потребителя → отметка в `TODO.md` и обновление памяти проекта.

Skill — **оркестратор**: свой поиск багов он не изобретает, а вызывает `review-code` (пол уровня —
`xhigh`, при касании security-поверхности или контрактов — `max`) и `/dev-toolkit:cppr`; файл
описания PR с метаданными проходов ревью (они есть только у него) собирает сам и передаёт `cppr`.

Вызов вручную: `/dev-toolkit:todo-ship`; срабатывает и по описанию — «закрой пункт 3 из TODO»,
«сделай пункт TODO под ключ», «реализуй и доведи до мёржа».

> ⚠️ Необратимая часть — под двумя раздельными санкциями: первая (шаг 1) разрешает **мёрж**,
> вторая — **выдачу результата потребителю** и берётся перед тем действием, которое выпускает
> изменение наружу: перед тегом или деплоем, а там, где релизом является сам мёрж (версия в
> манифесте) — до мёржа, потому что после него отменять уже нечего. Мёрж, теги и деплой не заведены
> в `allowed-tools`, поэтому проходят обычный permission-промпт; пуш и создание PR авто-одобрены
> внутри `/dev-toolkit:cppr`, которому skill их делегирует.

С 1.19.0 skill совместим с проектными хуками-гейтами: файл описания PR с метаданными ревью
передаёт аргументом `/dev-toolkit:cppr` (тот сверяет его с требованиями проекта до коммита и зовёт
`gh pr create --body-file`), передаёт `review-code` номер прохода, перед мёржем ждёт **все** проверки и судит
их по `gh pr checks <N> --json name,state`, а не по коду выхода (незелёная только необязательная
проверка в проекте без гейта мёржа — вопрос пользователю), и мержит `gh pr merge <N>` с явным
номером.

#### Skill: statusline-setup

Настройка строки статуса Claude Code: `user@host:папка | модель ◔ effort | Context NN% | 5h NN% | 7d NN% | ветка`.

- `Context` — процент заполнения контекстного окна; до первого ответа API его нет.
- `5h` и `7d` — сколько **израсходовано** лимита подписки в пятичасовом окне и за неделю (остаток — 100
  минус значение). Данные есть только при подписке claude.ai (Pro/Max) и после первого ответа API; при
  работе по API-ключу сегментов нет, каждое окно может отсутствовать отдельно.
- `effort` — текущий уровень (`low`…`max`), меняется вместе с `/effort`; у модели без effort выводится
  одно название. Если вместо `◔` виден `□` — в шрифте нет U+25D4, замени в скрипте `\xe2\x97\x94` на
  другой символ (например, `\xc2\xb7` — `·`).
- Из названия модели и из показываемой папки убираются управляющие символы — имя каталога с
  escape-последовательностью или переводом строки строку статуса не перепишет.
- Цвет у всех трёх процентов один: до 59% без цвета, 60–79% жёлтый, от 80% красный.

Скрипт запускается по событиям сессии — среди них старт сессии, новое сообщение ассистента, `/compact`,
смена режима разрешений, наступление времени сброса окна лимита (после него окно пропадает из данных, и
сегмент исчезает до следующего ответа API), — в простое строка не обновляется. Чтобы обновлялась, добавь в
секцию `statusLine` файла `~/.claude/settings.json` поле `"refreshInterval": 30` (секунды, минимум 1);
скилл его сам не ставит. Таймер перезапускает скрипт на тех данных, что уже есть у Claude Code: ветка
git обновится, а проценты лимитов — только после следующего ответа API этой сессии (расход в других
сессиях и в claude.ai до него не виден).

Срабатывает автоматически по описанию — достаточно написать в чате:
«настрой statusline», «setup statusline», «установи statusline». Skill
проверяет текущий `~/.claude/settings.json`: если `statusLine` не настроен —
создаёт `~/.claude/statusline.sh` и прописывает конфигурацию; если уже настроен
на `~/.claude/statusline.sh` — покажет полный diff с новым шаблоном и спросит,
перезаписать ли; если на другую команду — спросит, заменить ли её.

**Мост в tmux.** Внутри tmux скрипт дополнительно пишет процент контекста в пользовательскую опцию
панели `@claude_ctx` (целое число; значения нет — опция снята). Сам tmux этого числа узнать не может,
а из опции его показывает строка статуса tmux — например, на узком экране телефона, где строка статуса
Claude Code не помещается. Вне tmux мост ничего не делает.

> Обновление плагина **не меняет** уже установленный `~/.claude/statusline.sh`. Чтобы получить мост
> (и любую новую версию шаблона), запусти скилл ещё раз: он покажет diff с новым шаблоном и спросит,
> перезаписать ли.

Строку статуса tmux скилл не трогает — добавь сегмент в `~/.tmux.conf` сам. Сегмент ставится **в
начало** твоего `status-right` (в примере после него — штатное значение tmux), длину нужно поднять:
штатные 40 знаков обрежут строку.

```tmux
set -g status-right-length 60
set -g status-right '#{?#{m/r:^[0-9][0-9]?[0-9]?$,#{@claude_ctx}},CTX #{@claude_ctx}%% | ,}"#{=21:pane_title}" %H:%M %d-%b-%y'
```

Что нужно знать:

- **Значение — ввод, а не число.** Записать опцию может любой процесс с доступом к сокету tmux, поэтому
  пример проверяет его самим форматом (`#{m/r:…}` — 1–3 цифры). **Не подставляй `#{@claude_ctx}` в
  команду внутри `#(…)` без такой проверки:** строка в `#(…)` уходит в `sh -c`. `#{q:…}` не защита:
  прямая форма `#{q:@claude_ctx}` экранирует пробел, `;`, `$` и обратную кавычку, но не перевод строки,
  а вложенная `#{q:#{@claude_ctx}}` не экранирует ничего. Неэкранированное `{1,3}` в регулярке ломает
  формат (запятая — разделитель полей); экранированная форма — `{1#,3#}`.
- **Не задавай `@claude_ctx` выше панели** (`set -g`, `set -w`, `set -s`): формат читает опцию с
  наследованием, и значение уровнем выше подменит число панели, а мост начнёт писать на каждом вызове.
- **Опция переживает выход из Claude.** Старое число остаётся в панели, пока в ней снова не запустят
  Claude. Чтобы не видеть его в обычном shell, добавь в условие команду панели:
  `#{&&:#{==:#{pane_current_command},claude},#{m/r:…}}` (имя процесса зависит от способа установки —
  проверь `tmux display -p '#{pane_current_command}'`).
- **Claude не в своей панели.** `TMUX` и `TMUX_PANE` наследует любой процесс, запущенный из панели, —
  например, терминалы редактора, открытого командой из tmux. Claude в таком терминале пишет в
  панель-родителя; несколько таких сессий перебивают друг друга.
- **Требования моста:** tmux 3.0 и новее; утилита `timeout` с ключом `-s` (GNU coreutils; BusyBox от
  1.30; на macOS — `brew install coreutils`). Без них мост молча не работает, строка статуса Claude Code
  цела.
- Мост не задерживает строку статуса: вызов tmux идёт в фоне и ограничен одной секундой, запись
  делается только при изменении значения.

#### Skill: optimize-project-docs

Оптимизация и реконсиляция проектной документации: сжать раздутый `CLAUDE.md`,
убрать устаревшее из памяти проекта Claude Code (`MEMORY.md` + каталог `memory/`),
синхронизировать факты между `CLAUDE.md`, `README`, памятью и companion-файлами
(`doc/DECISIONS.md` / `doc/REFERENCES.md`), вынести историю/справку в
companion-файлы — **без потери обоснований «почему»**. Это оптимизация
существующих доков, не написание новых.

Срабатывает автоматически по описанию — достаточно написать в чате: «оптимизируй
CLAUDE.md», «убери устаревшее из памяти проекта», «полная реконсиляция документации»,
«вынеси историю в DECISIONS», «optimize project docs». Skill режет только
устаревшее / дубли / противоречия / воду, сохраняя иерархию детализации (память
подробнее `CLAUDE.md` подробнее `README`); при противоречиях источник истины —
код и `git log`. Итог — отчёт единого формата: таблица ДО/ПОСЛЕ (строки, КБ,
≈токены), починенные противоречия, список «что не резал и почему». Сам не
коммитит без запроса — предлагает команды-обёртки (напр. `/dev-toolkit:cppr`)
или обычный commit/PR-флоу.

#### Skill: server-disk-cleanup

Анализ места на диске Linux-сервера или dev-машины и согласованная очистка. Фазы: разведка только
чтением (`du`, Docker — образы/тома/кеш сборки, журнал systemd, apt, старые ядра, кеши разработчика,
каталоги сессий Claude Code) → проверка «не используется ли» (упоминания образов в коде и
документации, `FROM`/`COPY --from`, остановленные контейнеры, процессы, «холодность» по самому
свежему файлу) → таблица кандидатов → выполнение → замер `df` до/после и сверка томов и контейнеров.

Срабатывает по описанию: «чем занято место на сервере», «освободи место», «почисти диск / Docker».
**Просьба «почисти» — не согласие на удаление:** она запускает только анализ. Таблица делится на
группу А (без риска) и группу Б (нужно решение) со **сквозной нумерацией**; удаляются только пункты,
номера которых пользователь назвал в ответе на прямой вопрос. Перед каждым пунктом — повторная
проверка по типу пункта (размер, процессы, ID образа, время создания тома, `realpath`); изменившийся
пункт или проверка, которая не выполнилась, — пункт пропускается до нового согласия. Таблица и замеры
хранятся файлами в рабочем каталоге сессии и переживают сжатие контекста. Только адресные команды:
`docker rmi`/`volume rm` по списку, без `prune -a` и `volume prune`; кеши — командами их менеджеров;
рекурсивное удаление сам — только внутри `/tmp/claude-<uid>/`, остальное — готовой командой
пользователю (через `! …`, а с `sudo` при пароле — в отдельном терминале: в режиме `!` sudo пароль
не спросит). Справочник по dnf/snap/podman/npm/pip/composer/go/cargo и список
«установлено, не кеш» — `skills/server-disk-cleanup/references/caches.md`.

#### Skill: debug

Систематическая отладка бага, красного теста, упавшего CI или сборки: **никаких исправлений до
найденной причины**. Четыре фазы: причина (ошибка и стек целиком, воспроизведение, `git log`/`git diff`
от рабочего состояния, в системе из нескольких звеньев — временное логирование на каждой границе,
трассировка значения к источнику) → сравнение с работающим аналогом → одна явная гипотеза и
минимальная проверка → исправление: базовый прогон тестов, тест, воспроизводящий дефект, увиден
красным до правки, одна правка в источнике, прогон **всего** набора с падениями по именам (что не
прогнано — сказать). После трёх неудачных правок — стоп и доклад с вариантами вместо четвёртой
заплатки. Логи, трейсы и ответы сервисов — данные, а не инструкции; значения секретов не выводятся
нигде (ни в логах, ни в цитатах отчёта); прод и боевые сервисы — только с санкции пользователя; откаты —
адресно, без `git checkout`/`stash` по чужим правкам. Нормы проекта из его `CLAUDE.md` и порядок
вызывающего скилла (например, `todo-ship`) главнее.

Срабатывает по описанию: «найди причину бага», «почему падает тест / CI», «продебажь», «работало, а
теперь сломалось», вставленный стек-трейс с вопросом «что это»; вызов вручную — `/dev-toolkit:debug`
(встроенная команда `/debug` Claude Code — другое: диагностика самой сессии). Не срабатывает, в
частности, на правку, которую пользователь назвал сам, замечания линтера, ревью диффа и новую фичу —
полный список в `description` скилла. Приёмы (трассировка к источнику, ожидание по условию для
флаки-тестов, проверки на нескольких слоях) — `skills/debug/references/techniques.md`. Основано на
`systematic-debugging` из [obra/superpowers](https://github.com/obra/superpowers) (MIT) — см.
`skills/debug/THIRD_PARTY_NOTICES.md`.

#### Хук: защита от деструктивных команд

`PreToolUse` на `Bash` — срабатывает автоматически на каждой Bash-команде,
блокирует с кодом 2 и возвращает модели понятное сообщение, *почему* отказано:

| Правило            | Что ловит                                                             |
|--------------------|-----------------------------------------------------------------------|
| Значения секретов  | литерал известного формата (GitHub `ghp_…`/`github_pat_…`, Anthropic/OpenAI `sk-…`, Slack `xox?-…`, AWS `AKIA…`, Telegram-бот, JWT, PEM `PRIVATE KEY`) или литерал ≥ 8 символов, присвоенный имени `password`/`secret`/`token`/`api_key` (`--password=…`, `API_KEY: …`); ссылка `$VAR` и путь к файлу пропускаются. Имена классов/тестов/путей со словом `Token` больше не блокируются |
| Вывод окружения    | голые `printenv`/`env`/`export`/`set`/`declare`/`typeset` (допустимы только флаги, например `export -p`), `docker compose config`, `docker`/`podman`/`kubectl … exec … env`, `/proc/*/environ` |
| `rm -r`/`rm -rf`/`rm --recursive` | рекурсивное удаление — флаг ловится в любой позиции аргументов (`rm -v -r x`, `rm x -r`) и в короткой, и в длинной форме, в т.ч. в составных командах (`a && b`, `;`, `\|`, `\|\|`); **исключение: `/tmp` и его содержимое разрешены** |
| `git reset --hard` | потеря незакоммиченных изменений                                      |
| `git push --force` | перезапись истории на remote (`--force`, `-f`, `--force-with-lease`)  |
| `git branch -D`    | принудительное удаление ветки (безопасный `-d` пропускается)          |
| `.env`-файлы       | fail-closed: любое обращение к `.env`/`.env.<суффикс>` (включая `grep`/`sed`/`source`/интерпретаторы/`cp`, glob `.env*`/`.env{,}`, кавычки внутри имени `.e""nv`, `f=.env`), кроме `ls`/`stat`/`test`/`[`/`[[`/`git status`/`git check-ignore`; шаблоны `.env.example`/`.env.dist`/`.env.sample` свободны. Перенаправление в `.env` или из него (`ls > .env`, `… < .env`) блокируется у любой команды. **Упоминание в тексте сообщения не блокируется** в строгих формах, в том числе внутри цепочки (см. «Особенности»): `git commit -m "…"`, `gh pr/issue … --title/--body "…"`; одиночный `echo`/`printf` (`echo "… .env"`, `echo .env >> .gitignore`) — только отдельной командой |

Особенности:

- **Секреты проверяются первыми и блокируются без эхо команды** — текст команды
  (например `export API_KEY=…`) не возвращается модели и не попадает в логи.
  Защита — от *случайной* утечки значения в текст команды, не от целенаправленного
  обхода: кавычки и экранирование не разбираются.
  Для остальных правил команда показывается (она безопасна и полезна для диагностики).
- **Текст сообщения коммита или PR — не команды**: упоминание `rm -rf`,
  `git push --force`, `printenv` или `.env` в тексте не блокируется для строгих форм
  `git commit … -m "…"` (или `-F - <<'EOF'`, или `-m "$(cat <<'EOF'` … `EOF` / `)"`),
  `gh pr|issue create|edit|comment|merge … --title/--body "…"` (или `--body-file - <<'EOF'`)
  — в том числе внутри цепочки (`cd x && git add … && git commit … && git push`):
  команды до и после сообщения проверяются как обычно. Одиночный `echo`/`printf` —
  тоже текст. Текст в `"…"` — без `$`, `` ` ``, `\`; флаги — из короткого списка;
  конвейер `|` сразу после команды-сообщения — не шаблон. Всё остальное
  (`cat <<'EOF' > файл`, `(echo …)`, тела here-doc у других команд) проверяется
  целиком, как команды: общий разбор «данные или код» по грамматике bash ненадёжен.
- **Любой сбой хука — блокировка**: выход с кодом, отличным от 0 и 2, превращается в 2.
- **Defense in depth.** Хук дополняет `permissions.deny` в `settings.json`:
  даёт явную причину блокировки и ловит то, что permissions не покрывают
  (например чтение `.env` разными утилитами). Хук судит текст команды до её
  запуска, поэтому неполный glob (`cat .en?`) или путь через переменную/файл-
  посредник он не различит — это закрывает только sandbox Claude Code
  (`sandbox.filesystem.denyRead`), ограничение на уровне ОС.
- Посмотреть/отключить хук — меню `/hooks`.

#### Хук: напоминание после компакции

`SessionStart` с matcher `compact` — срабатывает сразу после сжатия контекста (ручной `/compact`
или автоматического) и печатает в stdout короткое напоминание, которое попадает в контекст модели:
сводка компакции неточна в деталях, поэтому перед продолжением стоит перечитать рабочие файлы
задачи и проверить `git status`/ветку.

- **Рабочие файлы** ищутся только в `<проект>/.dev/` и `<проект>/.dev_files/` (без вложенных
  каталогов) по шаблонам `PLAN-*.md` и `HANDOFF*.md`; корень проекта не просматривается. Выводятся
  до 3 самых свежих по времени изменения (с датой `ДД.ММ`) вместе с корнем проекта; файлы старше
  14 дней и с временем изменения в будущем не показываются. Нет подходящих файлов — только общий
  текст.
- **Имя файла попадает в контекст модели**, поэтому пропускаются только имена из букв (включая
  кириллицу), цифр, пробела и `. _ - + , ( )`: управляющие и невидимые символы (разрывы строк
  Unicode, bidi, zero-width) и обратная кавычка отбрасывают файл. Файлы, отслеживаемые git,
  пропускаются: рабочие файлы держат вне git, а закоммиченный `.dev/` чужого репозитория —
  недоверенный текст. Симлинк `.dev` на каталог читается, симлинки на отдельные файлы — нет.
- Каталог проекта берётся из `$CLAUDE_PROJECT_DIR` (запасной — `$PWD`). Скрипт всегда завершается
  с кодом 0 и не зависит от `jq`. Нужен GNU `find` (Linux): на macOS/BSD строка со списком файлов
  не выводится, общий текст — всегда.
- В напоминание не входят: `REVIEW.md` — ревью перечитывает его само на фазе 0; `MEMORY.md` —
  Claude Code перечитывает индекс памяти после компакции вместе с `CLAUDE.md`; `doc/TODO.md` —
  связь с пунктом TODO ведёт чек-лист плана.
- Тест: `bash plugins/dev-toolkit/hooks/tests/test-post-compact-reminder.sh`.

#### Хук: звуковые уведомления

`Notification` + `Stop` — воспроизводят сигнал, когда Claude ждёт твоего
ответа/разрешения и когда завершил работу:

| Событие        | Когда срабатывает                 | Звук                         |
|----------------|-----------------------------------|------------------------------|
| `Notification` | Claude ждёт ответа или разрешения | `message` (1 гудок fallback) |
| `Stop`         | Claude закончил работу            | `complete` (2 гудка fallback)|

Особенности:

- **Универсальный подбор бэкенда.** Скрипт `notify-sound.sh` перебирает плееры
  (`pw-play` → `paplay` → `ffplay` → `play` → `aplay` → `canberra-gtk-play`)
  и системные звуки (`/usr/share/sounds/freedesktop/…`). Если плеера нет
  (например чистая tmux/SSH-сессия) — падает на **terminal bell** (`\a`):
  разное число гудков для двух событий.
- **Никогда не блокирует Claude** — хук всегда завершается кодом 0.
- Посмотреть/отключить — меню `/hooks`.

**Куда уйдёт звук при работе через SSH**

Хук исполняется **на той машине, где запущен Claude Code**. Если ты
подключаешься с ноутбука по ssh/tmux к серверу, важно, какой из двух
механизмов сработает:

- **Terminal bell (`\a`) — дойдёт до ноутбука.** Звонок — это байт `0x07`
  в потоке вывода терминала. Он едет по тому же каналу, что и весь текст:
  хук на сервере → tmux (при `bell-action any` пробрасывает звонок клиенту)
  → SSH → твой локальный эмулятор терминала пикает. Звук издаёт
  **локальный терминал на ноутбуке**, поэтому ты его слышишь.
- **Системные мелодии через плеер (`paplay` и т.п.) — останутся на сервере.**
  Плеер рендерит звук в звуковую карту той машины, где исполняется хук.
  SSH по умолчанию аудио не пробрасывает (в отличие от текстового потока
  и опционального X11), а на сервере звуковой карты обычно и нет. Чтобы
  мелодия с сервера зазвучала на ноутбуке, понадобилась бы сетевая
  переадресация PulseAudio/PipeWire — отдельная нетривиальная настройка.

**Вывод:** при работе по ssh/tmux выбирай **Вариант A (terminal bell)** —
только он реально доходит до ноутбука. **Вариант B (плеер)** имеет смысл,
когда Claude Code запускается прямо на ноутбуке в десктоп-сессии.

<details>
<summary>Вариант A. Только terminal bell (без установки пакетов)</summary>

Подходит, когда работаешь в терминале/tmux/SSH и не хочешь ставить плеер.
По умолчанию tmux перехватывает символ звонка (`\a`) и не пробрасывает его
в эмулятор терминала — чтобы гудок было слышно, добавь в `~/.tmux.conf`:

```tmux
# Пробрасывать звонок (bell) во все окна и в эмулятор терминала
set -g bell-action any
set -g visual-bell off
```

Применить без перезапуска tmux:

```bash
tmux source-file ~/.tmux.conf
```

Затем включи **audible bell** в самом эмуляторе терминала (GNOME Terminal:
*Preferences → Profile → Terminal bell*; Konsole, xterm и др. — аналогично).
Без поддержки звонка на стороне эмулятора гудка не будет — это ограничение
терминала, а не хука.

</details>

<details>
<summary>Вариант B. Системные мелодии (через плеер)</summary>

Даёт нормальный звук вместо гудка — отдельные мелодии для «жду ответа»
и «готово». Поставь плеер и тему звуков:

```bash
# Debian/Ubuntu
sudo apt install pulseaudio-utils sound-theme-freedesktop

# Fedora
sudo dnf install pulseaudio-utils sound-theme-freedesktop

# Arch
sudo pacman -S libpulse sound-theme-freedesktop
```

`pulseaudio-utils` даёт `paplay`, `sound-theme-freedesktop` — файлы
`/usr/share/sounds/freedesktop/stereo/{message,complete}.oga`. Скрипт
подхватит их автоматически, правок не требуется. Проверить вручную:

```bash
paplay /usr/share/sounds/freedesktop/stereo/complete.oga
```

> Помни про SSH-нюанс выше: мелодии плеера звучат на машине, где запущен
> Claude Code, и для них нужен работающий звуковой сервер (PipeWire/PulseAudio)
> и аудиоустройство. Для звука именно на ноутбуке через ssh/tmux используй
> Вариант A.

</details>

## Обновление

> Если в настройках маркетплейса (меню `/plugin`) **не включено автообновление** этих плагинов, обновляй их вручную командами ниже. При включённом автообновлении свежие версии подтягиваются сами, и эти шаги не нужны.

Сначала обнови каталог маркетплейса, затем нужные плагины. Скиллы (`review-code`, `todo-ship`, `statusline-setup`, `optimize-project-docs`, `server-disk-cleanup`, `debug`, `chat-handoff`) обновляются вместе со своим плагином — отдельной команды для них нет. Исключение — файлы, которые скилл создал у тебя: `~/.claude/statusline.sh` от `statusline-setup` обновляется только повторным запуском скилла.

```bash
/plugin marketplace update leonid74-ai-skills
/plugin update chat-handoff@leonid74-ai-skills
/plugin update dev-toolkit@leonid74-ai-skills
/plugin update andrej-karpathy-skills@leonid74-ai-skills
```

Обновление плагинов происходит только при изменении поля `version` в `plugin.json`.
Следи за релизами: [https://github.com/Leonid74/ai-skills](https://github.com/Leonid74/ai-skills)

### Синхронизация vendor-копии chat-handoff

Скилл `chat-handoff` включён как vendor-копия из [Leonid74/ai-skill-chat-handoff](https://github.com/Leonid74/ai-skill-chat-handoff). При выходе новой версии синхронизируй вручную — скачай свежий `SKILL.md` напрямую из upstream:

```bash
curl -fsSL https://raw.githubusercontent.com/Leonid74/ai-skill-chat-handoff/main/SKILL.md \
  -o plugins/chat-handoff/skills/chat-handoff/SKILL.md
```

Если в upstream поднялась версия (frontmatter `version:` в `SKILL.md`), синхронно подними `version` в `plugins/chat-handoff/.claude-plugin/plugin.json` — иначе пользователи не получат обновление. После — закоммить и запушь.
