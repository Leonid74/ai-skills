## Контекст

- Текущий git статус: !`git status`
- Текущий git diff (staged и unstaged изменения): !`git diff HEAD`
- Текущая ветка: !`git branch --show-current`
- Недавние коммиты: !`git log --oneline -10`

## Твоя задача

На основании вышеуказанных изменений:

1. Определи стек проекта по файлам в корне и запусти соответствующие проверки. Убедись, что все зеленые:
   - **PHP** (`composer.json`): `composer test` / `./vendor/bin/phpunit`, `composer cs-check`, `composer phpstan`
   - **Go** (`go.mod`): `go build ./...`, `go vet ./...`, `go test ./...`, `golangci-lint run` (если установлен)
   - **JS/TS** (`package.json`): `npm test`, `npm run lint`, `npm run format:check` (или аналоги из секции `scripts`)
   - Другой стек — найди и запусти его тесты, линтер и проверку форматирования.
   Запускай только те команды, которые реально объявлены в проекте (`composer.json` → `scripts`, `package.json` → `scripts`, `Makefile`). Несуществующие пропускай, не выдумывай.
   Если эти же проверки уже были прогнаны в текущей сессии и дифф с тех пор не менялся — не гоняй их повторно: сошлись в ответе на уже полученный зелёный результат. При любом сомнении (дифф менялся, прогонов в сессии не было) — прогоняй.
2. Создай новую ветку с осмысленным названием, если сейчас находишься в main/master. Если изменения разноплановые - предложи создать несколько веток.
3. Если видишь рассогласование CLAUDE.md, README.md или CHANGELOG.md с изменениями — НЕ правь эти файлы молча: перечисли найденные рассогласования отдельным списком в ответе (что и где устарело). Правки доков, внесённые на этом шаге, обходят ревью, которое вызывающий флоу уже провёл по текущему диффу, — решение об их внесении принимает вызывающая сессия/пользователь.
4. Сгенерируй описание для коммита каждой ветки: что изменено и почему, предложи title в формате Conventional Commits.
5. Создай один или несколько коммитов с вышеуказанными описаниями в нужной последовательности. Многострочное сообщение коммита — файлом через `Write` и `git commit -F <файл>`, а не heredoc в строке команды (см. п. 9 про хуки на текст команды).
6. Запушь ветку/ветки в origin с установкой upstream (`git push -u origin <ветка>`).
7. Подготовь **файл описания PR** (заголовок — отдельно, в формате Conventional Commits):
   - **Готовый файл от вызывающей стороны** (флоу или пользователь назвал путь к файлу описания) — использовать его **как есть**, не переписывать и не сокращать: метаданные ревью в нём собраны тем, кто ревью проводил.
   - **Готового файла нет** — сгенерировать описание (что изменено и почему) и записать через `Write` во временный файл **вне отслеживаемого дерева** (временный каталог сессии или игнорируемый git-каталог проекта вроде `.dev/`), путь — абсолютный. Если в текущей сессии проводилось ревью диффа (`/dev-toolkit:review-code` или конвейер проходов проекта), в файл входят его метаданные — по образцу:
     - таблица проходов: проход, уровень, range/target, агенты, минуты, токены (из сводки прогона `review-code`; неизвестное — `—`, а не выдуманное число);
     - таблица триажа: находка, статус (`CONFIRMED`/`PLAUSIBLE`), класс/исход, если проект их ведёт;
     - что вынесено владельцу, follow-up, пункты `TODO`, заведённые по ревью, и факт деградированного режима, если ревью шло без скилла.
   - **Требования проекта к описанию PR** (`CLAUDE.md`, `doc/REVIEW.md`: обязательные разделы, слова-маркеры, таблицы) — выполнить их в файле. Если ревью в сессии не было, а проект требует его метаданных, — не выдумывать проходы и токены: остановиться и сказать, что описание PR требует метаданных ревью, которых в сессии нет.
8. Перечисли файлы, измененные относительно main/master.
9. Создай PR: `gh pr create --body-file <файл> --title "<заголовок>"` — описание **только через `--body-file`**, никогда через `--body` или heredoc. Причина: проекты держат `PreToolUse`-хуки на текст Bash-команды (страж метаданных ревью в описании PR), которые судят строку команды целиком — текст описания в ней даёт ложные блоки, а описание без файла такой страж не пропускает. По той же причине `--body-file` ставить первым, а в заголовке не использовать `&`, `|`, `;`. Если хук всё же заблокировал `gh pr create` — прочитать причину из сообщения и исправить **файл описания**, а не переписывать команду в обход хука.
10. Вместе со ссылкой на PR выведи напоминание: ветка запушена с upstream, поэтому повторный локальный ревью (`/dev-toolkit:review-code`, `/code-review`) теперь требует явный target (`<уровень> <default-branch>...HEAD` или номер PR) — дефолтный scope после пуша пуст.
11. У тебя есть возможность вызывать несколько инструментов в одном ответе. Делай все вышеперечисленное минимальным числом ходов: независимые вызовы — одним блоком; `Write` файла описания PR и сообщения коммита — до команд, которые их читают. Не используй другие инструменты, кроме объявленных, и не делай ничего другого.
