## Контекст

- Текущий git статус: !`git status`
- Текущий git diff (staged и unstaged изменения): !`git diff HEAD`
- Текущая ветка: !`git branch --show-current`
- Недавние коммиты: !`git log --oneline -10`
- Аргументы вызова (необязательный путь к готовому файлу описания PR): $ARGUMENTS

## Твоя задача

На основании вышеуказанных изменений:

0. **Источник описания PR — до коммита и пуша.** Всё, из-за чего PR создать нельзя, выясняется здесь, а не после `git push`: иначе останется запушенная ветка без PR.
   - Прочитать требования проекта к описанию PR (`CLAUDE.md`, `doc/REVIEW.md` / `REVIEW.md`, если есть: обязательные разделы, слова-маркеры, таблицы).
   - **Готовый файл** — путь из аргументов вызова или явно названный вызывающим флоу. Прочитать его и сверить с требованиями проекта. Не хватает обязательного — **не** дописывать чужой файл (метаданные в нём собраны тем, кто проводил ревью) и не коммитить: остановиться и назвать вызывающей стороне, чего не хватает.
   - **Готового файла нет** — описание генерируется на шаге 7. Если проект требует метаданных ревью, а ревью текущего диффа в сессии не было (или после последнего прогона дифф менялся — см. шаг 7), остановиться **здесь**, до коммита: сказать, что описание PR требует метаданных ревью, которых нет, и предложить сначала провести ревью.
1. Определи стек проекта по файлам в корне и запусти соответствующие проверки. Убедись, что все зеленые:
   - **PHP** (`composer.json`): `composer test` / `./vendor/bin/phpunit`, `composer cs-check`, `composer phpstan`
   - **Go** (`go.mod`): `go build ./...`, `go vet ./...`, `go test ./...`, `golangci-lint run` (если установлен)
   - **JS/TS** (`package.json`): `npm test`, `npm run lint`, `npm run format:check` (или аналоги из секции `scripts`)
   - Другой стек — найди и запусти его тесты, линтер и проверку форматирования.
   Запускай только те команды, которые реально объявлены в проекте (`composer.json` → `scripts`, `package.json` → `scripts`, `Makefile`). Несуществующие пропускай, не выдумывай.
   Если эти же проверки уже были прогнаны в текущей сессии и дифф с тех пор не менялся — не гоняй их повторно: сошлись в ответе на уже полученный зелёный результат. При любом сомнении (дифф менялся, прогонов в сессии не было) — прогоняй.
2. Создай новую ветку с осмысленным названием, если сейчас находишься в main/master. Если изменения разноплановые - предложи создать несколько веток.
3. Если видишь рассогласование CLAUDE.md, README.md или CHANGELOG.md с изменениями — НЕ правь эти файлы молча: перечисли найденные рассогласования отдельным списком в ответе (что и где устарело). Правки доков, внесённые на этом шаге, обходят ревью, которое вызывающий флоу уже провёл по текущему диффу, — решение об их внесении принимает вызывающая сессия/пользователь.
4. Сгенерируй описание для коммита каждой ветки: что изменено и почему, предложи title в формате Conventional Commits.
5. Создай один или несколько коммитов с вышеуказанными описаниями в нужной последовательности. Многострочное сообщение коммита — файлом во **временном каталоге сессии** (не в рабочем дереве: иначе файл уйдёт в `git add` и в коммит) и `git commit -F <абсолютный путь>`, а не heredoc в строке команды (см. п. 9 про хуки на текст команды).
6. Запушь ветку/ветки в origin с установкой upstream (`git push -u origin <ветка>`).
7. Подготовь **файл описания PR для текущей ветки** (заголовок — отдельно, в формате Conventional Commits; при нескольких ветках — свой файл на каждую, и готовый файл вызывающей стороны относится только к той ветке, для которой он собран):
   - **Готовый файл** (шаг 0) — использовать **как есть**, не переписывать и не сокращать.
   - **Готового файла нет** — сгенерировать описание (что изменено и почему) и записать во временный файл **вне отслеживаемого дерева** (временный каталог сессии или игнорируемый git-каталог проекта вроде `.dev/`), путь — абсолютный. Если в текущей сессии проводилось ревью диффа (`/dev-toolkit:review-code` или конвейер проходов проекта), в файл входят его метаданные — **только если после последнего прогона ревью дифф не менялся**; если менялся, это прямо написать в описании (какие файлы или коммиты ревью не видело), а не выдавать таблицу за ревью итогового кода. Образец:
     - таблица проходов: проход, уровень, range/target, режим (`полный`/`деградированный` с причиной — из поля «режим» сводки прогона `review-code`), агенты, минуты, токены (из сводки прогона; неизвестное или «недоступны» — `—`, а не выдуманное число);
     - таблица триажа: находка, статус (`CONFIRMED`/`PLAUSIBLE`; у прогона без верификации — `low`, fallback — `—`, вердикт не выдумывать), класс/исход, если проект их ведёт;
     - что вынесено владельцу, follow-up, пункты `TODO`, заведённые по ревью, и факт деградированного режима — как внутри скилла, так и если ревью шло без скилла.
   - Требования проекта из шага 0 — выполнить в сгенерированном файле.
8. Перечисли файлы, измененные относительно main/master.
9. **Перед публикацией** прочитать итоговый файл описания PR и файлы сообщений коммитов на значения секретов (ключи, токены, пароли, приватные ключи, строки `.env`): механический страж секретов в хуке судит только текст команды и содержимое файлов не видит. Значение найдено — не публиковать, заменить на `<секрет: ИМЯ>` в своём файле или остановиться, если файл чужой. Затем создай PR: `gh pr create --body-file <файл> --title "<заголовок>"` — описание **только через `--body-file`**, никогда через `--body` или heredoc. Причина: проекты держат `PreToolUse`-хуки на текст Bash-команды (страж метаданных ревью в описании PR), которые судят строку команды целиком — текст описания в ней даёт ложные блоки, а описание без файла такой страж не пропускает. По той же причине `--body-file` ставить первым, а в заголовке не использовать `&`, `|`, `;`. Если хук всё же заблокировал `gh pr create` — прочитать причину: для **своего** сгенерированного файла — исправить файл (не выдумывая метаданных), для **готового** файла — не трогать его и остановиться с причиной для вызывающей стороны; команду в обход хука не переписывать никогда.
10. Вместе со ссылкой на PR выведи напоминание: ветка запушена с upstream, поэтому повторный локальный ревью (`/dev-toolkit:review-code`, `/code-review`) теперь требует явный target (`<уровень> <default-branch>...HEAD` или номер PR) — дефолтный scope после пуша пуст. Если PR создать не удалось после пуша — прямо сказать, что ветка запушена, а PR нет, и что именно помешало.
11. У тебя есть возможность вызывать несколько инструментов в одном ответе. Делай все вышеперечисленное минимальным числом ходов: независимые вызовы — одним блоком; запись файла описания PR и сообщения коммита — до команд, которые их читают. Используй только инструменты, нужные для этих шагов (чтение файлов, запись во временный каталог, перечисленные команды), и не делай ничего другого. Запись файлов не авто-одобрена этой командой намеренно — она проходит обычное разрешение среды.
