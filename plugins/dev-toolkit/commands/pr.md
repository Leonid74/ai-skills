## Контекст

- Текущий git статус: !`git status`
- Текущий git diff (staged и unstaged изменения): !`git diff HEAD`
- Текущая ветка: !`git branch --show-current`
- Недавние коммиты: !`git log --oneline -10`

## Твоя задача

На основании вышеуказанных изменений подготовь Pull Request для текущей ветки.

1. Определи стек проекта по файлам в корне и запусти соответствующие проверки. Убедись, что все зеленые:
   - **PHP** (`composer.json`): `composer test` / `./vendor/bin/phpunit`, `composer cs-check`, `composer phpstan`
   - **Go** (`go.mod`): `go build ./...`, `go vet ./...`, `go test ./...`, `golangci-lint run` (если установлен)
   - **JS/TS** (`package.json`): `npm test`, `npm run lint`, `npm run format:check` (или аналоги из секции `scripts`)
   - Другой стек — найди и запусти его тесты, линтер и проверку форматирования.
   Запускай только те команды, которые реально объявлены в проекте (`composer.json` → `scripts`, `package.json` → `scripts`, `Makefile`). Несуществующие пропускай, не выдумывай.
   Если эти же проверки уже были прогнаны в текущей сессии и дифф с тех пор не менялся — не гоняй их повторно: сошлись в ответе на уже полученный зелёный результат. При любом сомнении (дифф менялся, прогонов в сессии не было) — прогоняй.
2. Сгенерируй описание PR: что изменено и почему.
3. Перечисли файлы, измененные относительно main.
4. Предложи title в формате Conventional Commits.
5. Если видишь рассогласование CLAUDE.md, README.md или CHANGELOG.md с изменениями — НЕ правь эти файлы молча: перечисли найденные рассогласования отдельным списком в ответе (что и где устарело). Правки доков, внесённые на этом шаге, обходят ревью, которое вызывающий флоу уже провёл по текущему диффу, — решение об их внесении принимает вызывающая сессия/пользователь.
6. Создай PR по правилам шагов 7 и 9 `/dev-toolkit:cppr`: описание — файлом во временном каталоге сессии (с требованиями проекта к описанию PR и без выдуманных метаданных ревью), проверка файла на значения секретов перед публикацией, затем `gh pr create --body-file <файл> --title "<заголовок>"` — никогда `--body` или heredoc: проектные хуки на текст Bash-команды иначе дают ложный блок или не пропускают описание без файла.
7. Вместе со ссылкой на PR выведи напоминание: если ветка уже запушена, повторный локальный ревью (`/dev-toolkit:review-code`, `/code-review`) — только с явным target (`<уровень> <default-branch>...HEAD` или номер PR) — дефолтный scope после пуша пуст.
8. У тебя есть возможность вызывать несколько инструментов в одном ответе. Делай все вышеперечисленное минимальным числом ходов: запись файла описания — до `gh pr create`. Используй только инструменты, нужные для этих шагов (чтение файлов, запись во временный каталог, перечисленные команды), и не делай ничего другого.
