# Оптимизация и реконсиляция проектной документации

**Цель:** уменьшить объём проектной документации и убрать рассинхрон между её слоями, **не потеряв ни одного
обоснования «почему»**. Три слоя:

1. **`CLAUDE.md`** (корень репо; бывают и вложенные) — инструкции и контекст для будущих сессий.
2. **`README.md`** — как пользоваться проектом.
3. **Память Claude Code** — индекс `MEMORY.md` + каталог `memory/` (по файлу на факт). Путь обычно
   `~/.claude/projects/<кодированный-путь-проекта>/memory/` и виден в контексте сессии. Если памяти нет — слой пропускается.

Скилл универсален: работает для любого стека. Если README или памяти нет — грациозно пропусти их.

## Принципы (прочитай до первой правки)

Это ядро. Нарушение любого пункта портит результат сильнее, чем оставленный лишний абзац.

- **Сокращай только из названного набора источников**, а не «на глаз»:
  1. **устаревшее / противоречивое** — утверждения, которые код/история опровергают, или которые конфликтуют
     с другим местом того же файла;
  2. **статус-маркеры и хвосты планирования** — «(этап N, готов)», «TODO позже», «следующий — этап N», после
     того как работа закрыта;
  3. **дублированные факты** — один и тот же факт, повторённый дословно в нескольких местах;
  4. **нарративная вода вокруг ловушки** — многословное пересказывание того, «что делает код» (реконструируемо
     из кода), вокруг непреложного факта.
- **Не прорежай обоснования «почему».** Объяснение, почему принято решение/почему есть ловушка — самое ценное в
  доках: именно оно не даёт будущим сессиям перерешивать закрытое и наступать на грабли. «Что делает код» —
  реконструируемо и сжимаемо; «почему так» — нет. При сомнении оставляй «почему».
- **Инвариант удаления:** прежде чем удалить строку, убедись, что её уникальный факт **уже есть в другом месте**.
  Если нет — не удаляй, а перефразируй короче или перенеси. Это страховка от тихой потери знания.
- **Реконсиляция ≠ устранение перекрытия.** Цель реконсиляции — убрать **противоречия** и выровнять факты между
  тремя слоями, **сохранив естественную иерархию детализации**: память подробнее `CLAUDE.md`, `CLAUDE.md`
  подробнее `README`. Перекрытие между ними **намеренно** — не режь память за то, что факт есть и в `CLAUDE.md`.
- **Объём режут в основном в `CLAUDE.md`.** По умолчанию `README` и память — **reconcile-only**: правь их только
  при противоречии или внутренней устарелости, объём не режь. Иначе — только если пользователь прямо попросил.
- **Память — снимок во времени.** Утверждения памяти о коде (файлы, флаги, статусы) могли устареть. Прежде чем
  считать факт из памяти основанием для правки — сверь с реальным кодом / `git log`.
- **Сохраняй язык и стиль целевых файлов.** Многие проекты англоязычны — не переводи и не меняй тон. Подстройся
  под существующую плотность комментариев, заголовки, формат.

## Процесс

### 0. Замер ДО

Сними метрики каждого затронутого файла — пользователю важно видеть эффект:

```bash
wc -l -c CLAUDE.md README.md   # строки и байты
# для памяти: wc -l -c "$MEMDIR"/*.md  и суммарно  cat "$MEMDIR"/*.md | wc -l -c
```

Сложи в таблицу «Файл | строк | байт (КБ)» — она понадобится для сравнения ДО/ПОСЛЕ.

### 1. Инвентаризация

Определи, что реально есть: корневой `CLAUDE.md` (и вложенные, если просили их тоже), `README.md`, память
(`MEMORY.md` + `memory/*.md`). Прочитай всё целиком перед правками.

**Не трогай без явной просьбы пользователя:** глобальный `~/.claude/CLAUDE.md`, `CHANGELOG.md` (append-only
история), `PROJECT_PLAN.md` и подобные планы, lock-файлы. Если пользователь явно просил один из них — можно.

### 2. Картирование (что резать и что чинить)

Пройди по принципам и собери кандидатов по 4 источникам. Параллельно отметь **противоречия** (одно место
говорит X, другое — не-X) — это первый приоритет, чинится всегда. Сверь сомнительные «факты» памяти с кодом.

При большом объёме покажи пользователю краткий план правок (что и почему режется) до начала — особенно если
затрагиваешь >2 файлов: правки документации трудно отменять выборочно, и согласие дешевле переделки.

### 3. Правки `CLAUDE.md`

- Предпочитай **точечные `Edit`** — они дёшевы для аудита и не рискуют тихо уронить факт.
- **Полный `Write`-рерайт** — только когда правок столько, что точечные нечитаемы. Тогда обязателен аудит на
  шаге 6 (`git diff --word-diff`): wholesale-перезапись легко роняет уникальный факт или вносит новое
  противоречие, и обычный взгляд этого не ловит.
- Сворачивай рассыпанные статус-маркеры в одну строку дорожной карты в шапке (напр. «этапы 1–9 закрыты»).
- Заголовки разделов с историческими метками этапов оставляй — это дешёвая навигация.

### 4. Память

- Сними **stale-within-memory**: хвосты «следующий — этап N», рамки «ждёт реализации» там, где закрыто,
  внутренние противоречия. Не де-дублируй против `CLAUDE.md` (см. принципы).
- **Сохраняй все файлы** (модель «один факт — один файл») и `[[links]]` между ними целыми.
- Если поменялся смысл поля `description:` во фронтматтере файла памяти — **синхронно обнови строку-хук в
  `MEMORY.md`** (это индекс, грузится каждую сессию; рассинхрон хука и файла — тоже рассинхрон).

### 5. Реконсиляция (сверка трёх слоёв)

Прогони сверку ключевых фактов по `CLAUDE.md` ↔ память ↔ `README.md`: статусы, что сделано/исключено, имена
сущностей, флаги. Цель — ноль противоречий при сохранённой иерархии. `README` и память правь при противоречии
или внутренней устарелости (как в принципах); **объём** в них не режь (если пользователь не просил).

### 6. Верификация

- **Grep**, что устаревшие маркеры вычищены (подставь свои паттерны проекта), напр.:
  ```bash
  grep -n 'следующий — этап\|ждёт реализации\|TODO позже' CLAUDE.md   # ожидается пусто
  ```
- Для файлов под git — **`git diff --word-diff` глазами**: пройди каждое удаление против инварианта (уникальный
  факт жив в другом месте? противоречие не внесено?). Память может лежать вне репо — тогда обычный просмотр.
- Собери таблицу **ДО/ПОСЛЕ** (строки и КБ, по файлам и суммарно) с % сокращения.
- Явный самоконтроль: «ни одно обоснование „почему" не удалено — только сжаты пересказы „что делает код"».

### 7. Хэндофф (коммит — отдельно)

Документацию обычно коммитят **отдельным коммитом** от кода. Сам **не коммить без запроса**. Если в окружении
есть команды-обёртки для коммита/PR (напр. `/cppr`, `/pr`) — предложи их; иначе предложи обычный commit/PR-флоу.
Если пользователь просил выполнить всё — сначала создай ветку (не коммить в `main`/`master` напрямую), затем
веди коммит/PR.

## Анти-паттерны (грабли этого процесса)

- **Гнаться за процентом ценой «почему».** Честные 20–25 % с сохранёнными обоснованиями лучше 40 % с вырезанной
  мотивацией решений. Процент — следствие, а не цель.
- **Де-дублировать память против `CLAUDE.md`.** Перекрытие намеренно; резать память за это — потеря глубины.
- **Сжимать `README`/память «заодно».** По умолчанию они reconcile-only.
- **Верить памяти как коду.** Снимок во времени; сверяй с реальностью перед правкой.
- **Удалять строку, чей факт нигде больше не зафиксирован.** Сначала перенеси/перефразируй.
- **Wholesale-рерайт без word-diff аудита.** Самый частый способ тихо потерять факт.
