# План: скилл `kod-review` в `dev-toolkit`

**Статус:** реализовано 2026-07-19 в `dev-toolkit 1.11.0` (PR #35) — скилл лежит в
`plugins/dev-toolkit/skills/kod-review/SKILL.md`. План подготовлен 2026-07-19 в сессии проекта
`sheikman.ru`, выполнен в сессии этого репозитория (`ai-skills`). Документ сохранён как запись
обоснований «почему» — актуальное поведение скилла смотреть в самом `SKILL.md`, а не здесь.

Отклонения от плана при реализации:

- `model: opus` для агентов поиска (§6) **не прописан** — жёсткий пин модели в проектонезависимом
  скилле протухает при смене поколения моделей; агенты наследуют модель сессии;
- в §6 фаза 3 поле `level` описано наравне с полями находки — фактически это **top-level**-параметр
  `ReportFindings`, а не поле внутри находки; в скилле сделано верно;
- живой прогон (§8) не выполнялся — валидация `claude plugin validate` пройдена.

---

## 1. Зачем

Встроенный в Claude Code скилл `code-review` (ревью рабочего диффа, уровни `low…max` + облачный
`ultra`) с версии CLI **2.1.215** помечен `disable-model-invocation`: Claude **не может** вызвать его
сам, только пользователь набирает `/code-review`. Проверено 2026-07-19: поддерживаемого способа
снять флаг нет — `skillOverrides` в `settings.json` управляет только видимостью (в бинарнике прямым
текстом: «on/name-only locked by frontmatter disable-model-invocation»), permissions-правило
`Skill(code-review)` флаг не переопределяет, env-переменной нет. Своя копия под именем `code-review`
затенила бы встроенный скилл целиком и убила его функциональность — отвергнуто.

Следствие: проектные флоу, где шаг «ревью диффа» обязателен (например «Флоу после реализации» в
`sheikman.ru/CLAUDE.md`), не могут выполняться автономно — сессия вынуждена либо просить
пользователя, либо каждый раз изобретать ревьюера-субагента заново.

**Цель скилла:** дать Claude вызываемый им самим пайплайн ревью того же класса — с калибровкой по
уровню, adversarial-проверкой находок и типизированным выводом в UI.

**Явно вне цели:** облачный `ultra`. Он серверный, платный и по системным правилам запускается
только пользователем; воспроизводить/обходить его нельзя. Скилл должен уметь **предложить**
пользователю набрать `/code-review ultra` — и не более того.

⚠️ **Промпты встроенного скилла не копировать.** Это проприетарный код Anthropic (тексты лежат в
бинарнике CLI). Весь текст скилла писать свой, опираясь на таблицу уровней из `CLAUDE.md` проекта
`sheikman.ru` — она подробнее дефолтной (security-поверхность, контракты клиент↔API, пороги по
размеру диффа) и служит **образцом структуры**, а не источником для копипаста в скилл: сам скилл
должен быть проектонезависимым и вычитывать специфику из `CLAUDE.md` целевого репозитория.

## 2. Имя и способ вызова

- Файл: `plugins/dev-toolkit/skills/kod-review/SKILL.md` (именно **skill**, не `commands/` — текст
  длинный, а скиллы грузятся по требованию).
- Вызов пользователем: `/dev-toolkit:kod-review <уровень> [target]` (плагинные артефакты всегда
  неймспейснуты — «голого» `/kod-review` не будет; зафиксировать это в README, чтобы не удивляло).
- Вызов моделью: `Skill(dev-toolkit:kod-review, args: "max master...HEAD")`. Ключевое — **не**
  ставить `disable-model-invocation` во frontmatter (по умолчанию скилл модель-вызываемый).

## 3. Frontmatter

```yaml
---
name: kod-review
description: "<одно предложение, что делает> \n\nInvoke for: <когда звать> \n\nSkip for: <когда не звать>"
allowed-tools: Bash(git status:*), Bash(git diff:*), Bash(git log:*), Bash(git branch:*), Bash(git merge-base:*), Bash(gh pr diff:*), Bash(gh pr view:*), Read, Grep, Glob, Agent, ReportFindings
---
```

Требования к `description` (по образцу `optimize-project-docs`): триггеры на русском **и**
английском, отдельный блок «Skip for» — чтобы скилл не перехватывал `/dev-toolkit:review`
(быстрое ревью рабочего диффа) и `/dev-toolkit:pr`.

Разграничение с уже существующими артефактами описать прямо в теле скилла:
- `review` / `review-last` — быстрый однопроходный обзор диффа, без уровней и без верификации;
- `kod-review` — многоугловой поиск + adversarial-верификация + типизированный вывод;
- `cppr` — коммит/пуш/PR, ревью не делает.

## 4. Аргументы и разрешение scope

Парсить `args` как `<уровень> [target]`:

- **уровень** (обязателен, если не передан — не угадывать по effort сессии, а определить по
  таблице §5 из фактического диффа и **сказать вслух**, какой уровень выбран и почему);
- **target** — одно из:
  - пусто → рабочий дифф: `git diff HEAD` (staged + unstaged); если пусто, то `git diff` против
    upstream: `git diff @{upstream}...HEAD`;
  - `<base>...<head>` (напр. `master...HEAD`) → `git diff <base>...<head>`;
  - число (`61`) → `gh pr diff 61`; метаданные — `gh pr view 61`.

⚠️ Ловушка, которую скилл обязан обрабатывать: **после пуша** ветка не впереди upstream, и
«дефолтный» scope оказывается пустым. Если вычисленный дифф пуст — не молчать и не рапортовать
«находок нет», а сообщить, что scope пуст, и предложить явный target (`<base>...HEAD` или номер PR).

Скилл всегда печатает первой строкой, **что именно** он ревьюит (target, число файлов, число строк) —
иначе невозможно отличить «чисто» от «нечего было смотреть».

## 5. Таблица уровней

Ядро скилла. Пишется своим текстом; структура — по образцу `sheikman.ru/CLAUDE.md`
(раздел «Выбор уровня ревью»), но **проектонезависимо**.

| Уровень | Когда | Углы поиска | Верификация |
|---|---|---|---|
| `low` | 1 файл, ≤ ~10 строк кода, вне security-поверхности | 2 | 1 голос |
| `medium` | 1–2 файла, ≤ ~50 строк, без контрактов и security | 3 | 1 голос |
| `high` | **дефолт** — всё, что не попало в соседние строки | 5 | 2 голоса |
| `xhigh` | крупный дифф (> ~5 файлов или > ~300 строк) без security | 7 | 2 голоса |
| `max` | security-поверхность или контракты (любое касание, независимо от размера) | 8–10 | 3 голоса, ≥2 «refuted» убивают находку |

Правила, которые надо перенести по смыслу (это то, чем наша таблица ценнее дефолтной):

1. **Триггеры `max` не зависят от размера** — любое касание security-поверхности или
   кросс-граничного контракта поднимает уровень до `max`, даже если это одна строка.
2. **Security-поверхность и контракты берутся из `CLAUDE.md` целевого проекта.** Скилл в начале
   работы читает корневой `CLAUDE.md` (и вложенные в затронутых каталогах) и извлекает: список
   security-чувствительных путей, дублирующиеся по обе стороны границы контракты, конвенции стиля
   и документирования. Если в проекте такого списка нет — применить дефолтную эвристику
   (аутентификация, криптография, работа с вводом, шаблоны/рендер, конфиги CI/CD и деплоя,
   права доступа, обработка загрузок) и **сказать**, что список выведен эвристически.
3. **Пороги размера считать по содержательному диффу** — не считать релизную механику:
   `CHANGELOG`, чисто механические бампы lock-файлов, сгенерированные артефакты.
4. **`low`/`medium` — precision** (мало находок, высокая уверенность, нитпики отбрасываются);
   **`high`…`max` — recall** (широкое покрытие, спорные находки допустимы, но помечаются
   как `PLAUSIBLE`, а не `CONFIRMED`).
5. Дифф без исполняемого кода (только доки/комментарии) — прямое чтение, без запуска пайплайна;
   скилл должен явно об этом сказать и не жечь агентов впустую.

## 6. Пайплайн

**Фаза 0 — контекст.** Прочитать `CLAUDE.md` целевого проекта; получить дифф; определить стек
(`composer.json` / `go.mod` / `package.json` / прочее); посчитать размер содержательного диффа;
объявить уровень (переданный или выведенный) и что ревьюится.

**Фаза 1 — поиск.** Запустить N независимых углов (N — из таблицы §5) через `Agent`
(`subagent_type: general-purpose`, `model: opus`), **параллельно, одним блоком вызовов**. Каждый
угол получает: полный дифф, извлечённые из `CLAUDE.md` правила, свой ракурс и требование вернуть
структурированный список. Ракурсы (брать первые N):

1. корректность и edge cases в самом диффе (без ухода в остальной репозиторий);
2. соответствие правилам `CLAUDE.md` целевого проекта (и только тем, что там реально написаны);
3. контракты/дубли по обе стороны границы: не разъехались ли парные значения (клиент↔API,
   конфиг↔код, скрипт сборки↔рантайм);
4. история: `git log`/`git blame` затронутых строк — не переоткрывается ли уже закрытый баг,
   не отменяется ли осознанное решение;
5. security: ввод без валидации, утечки секретов/путей/ПДн в логи и ответы, права, инъекции,
   ослабление заголовков/политик;
6. тесты: покрыта ли новая логика, не сломан ли смысл существующих тестов;
7. ошибкоустойчивость: обработка отказов, таймауты, fail-open против fail-closed, ретраи;
8. комментарии и документация: не разошлись ли PHPDoc/GoDoc/JSDoc и `CHANGELOG` с кодом;
9. производительность: лишние обходы, N+1, аллокации в горячем пути;
10. чистота: мёртвый код, дубликаты, ненужная сложность (только для `xhigh`/`max`).

**Фаза 2 — верификация.** Для каждой находки — независимые проверяющие (число голосов из §5),
которым задача сформулирована **на опровержение**: «попробуй доказать, что это ложное срабатывание;
при сомнении считай, что находка ложная». Находка выживает, если большинство не смогло опровергнуть.
Для `max` голоса давать с разными линзами (корректность / безопасность / воспроизводимость),
а не тремя одинаковыми скептиками.

Использовать `pipeline`-подход: верификация находок одного угла не должна ждать, пока досчитают
остальные углы. Если в репозитории доступен инструмент `Workflow` и пользователь дал явное согласие
на мультиагентную оркестрацию — можно оформить фазы 1–2 как workflow-скрипт; **по умолчанию —
обычные параллельные `Agent`-вызовы** (Workflow требует явного opt-in пользователя).

**Фаза 3 — вывод.** Дедуп по (файл, строка, суть) → сортировка по серьёзности → вызов
`ReportFindings` **один раз**, с полями `file`, `line`, `summary`, `failure_scenario`,
`short_summary` (≤60 символов, только утверждение), `category`, `verdict`
(`CONFIRMED` / `PLAUSIBLE`), `level`. Текстом находки дублировать нельзя — только через инструмент.
Если не выжило ничего — вызвать с пустым массивом и коротко сказать, что и на каком уровне проверено.

**Фаза 4 — предложения (не выполнять без спроса).**
- если уровень `max` и находки серьёзные — предложить пользователю `/code-review ultra` как
  независимую верификацию (запускает только он);
- предложить починить подтверждённые находки — но **не чинить молча**;
- если проектный `CLAUDE.md` требует сверки со вторым ревьюером — напомнить про `advisor`.

## 8. Проверка перед коммитом

```bash
claude plugin validate ./
claude plugin validate ./plugins/dev-toolkit
```

Плюс **живой прогон**: в любом рабочем репозитории с непустым диффом вызвать
`/dev-toolkit:kod-review low` и `Skill(dev-toolkit:kod-review, args: "high master...HEAD")` —
убедиться, что (а) модель действительно может вызвать скилл сама, (б) пустой scope после пуша
даёт внятное сообщение, а не «находок нет», (в) `ReportFindings` отрисовался в UI.

## 9. Риски и ограничения

- **Дороговизна.** `max` — это 8–10 углов × агент + до 3 голосов на находку. В скилле должно быть
  явно написано: не поднимать уровень «на всякий случай», а следовать таблице.
- **Ложная точность.** Свой пайплайн не эквивалентен встроенному: у того есть облачный режим и
  калибровка, которой у нас нет. В README и в самом скилле честно написать, что это
  **самостоятельный инструмент, а не эмуляция** `/code-review`.
- **Дрейф от CLI.** Если Anthropic снимет `disable-model-invocation` (перепроверка запланирована в
  `sheikman.ru/doc/TODO.md` п.11 на 2026-07-22 и 2026-07-26), скилл останется полезен как
  проектонастраиваемый вариант, но флоу проектов стоит вернуть на встроенный.
- **Неймспейс.** «Голого» `/kod-review` не будет — только `/dev-toolkit:kod-review`. Если хочется
  короткого имени, единственный путь — локальный скилл в `~/.claude/skills/kod-review/`, но тогда
  он не разъезжается по проектам вместе с плагином.
