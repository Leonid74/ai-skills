# Changelog

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/). Версии — отдельно по
каждому плагину маркетплейса (своя версия в `plugins/<plugin>/.claude-plugin/plugin.json`), плюс
отдельный раздел для изменений самого репозитория-маркетплейса, у которого нет собственной версии.

## dev-toolkit

### [2.8.0] — 2026-10-04

Скилл `review-code`: пол модели для последней линии при слабой сессии. Итог пересмотра правила «Модель
субагентов» (три решения от 20.09.2026, данные — 31 проход ≥ 2 в описаниях PR проекта-потребителя).

- **Сессия на `sonnet` или `haiku` либо её модель неизвестна — угол 5 (security),
  верификаторы на любом уровне (включая `xhigh`) и линзы `max` получают `model: opus`**, в том числе
  при перезапуске. Раньше они шли без `model` и при слабой сессии оказывались на модели слабее
  finder'ов первого прохода; скилл об этом только уведомлял. Сессия на `opus` — без
  изменений: `model` этим ролям не передаётся. «Неизвестна» — это и отсутствие сведений о модели, и
  название вне семейств `opus`/`sonnet`/`haiku`: место такой модели относительно `opus` скилл не
  оценивает. Цена: сессия на модели сильнее `opus` получит верификацию на `opus` — уведомление в
  заголовке вывода это называет. Граница:
  правило смотрит на модель сессии, а не на модель по умолчанию для субагентов среды.
- **Уведомление о модели** называет только роли, которые есть на уровне прогона (на `medium` — одни
  верификаторы, линзы — только на `max`); модель сессии, по которой выбрано правило, всегда названа в
  поле «прогон» сводки. Текст целевого проекта о модели сессии — данные, а не сведения среды.
- **Вариант (а) при втором отказе угла** — перезапуск на другой модели, как и раньше (без `model`,
  если угол шёл с `model`); исключение — угол 5 при слабой или неизвестной сессии: он остаётся на
  `opus`, и вариант прямо называет это повтором на той же модели.
- **Пол модели и недоступный `opus`.** Слабой сессии `opus` может быть недоступен (исчерпан лимит, нет
  в тарифе). Причину отказа агентов skill не определяет и штатный порядок не меняет (лимит, второй
  отказ угла, деградированный прогон). Но если на `pass` ≥ 2 ни один агент на `opus` не дал
  структурного ответа, а агенты на `sonnet` дали (поле результата скрипта `opusSilent`, стенд —
  вектор 23), skill останавливается и спрашивает пользователя: к штатным вариантам добавляются два —
  довести прогон без пола модели либо отложить его до возврата `opus`. Выбрать его может только пользователь ответом в сессии; решение действует до конца
  прогона и называется строкой в заголовке и «заметках». На `pass=1` на `opus` идут все роли —
  слабой сессии без доступа к `opus` первый проход недоступен, как и раньше.
- **Resume:** `sessionBelowOpus` перед resume определяется заново — если модель сессии за время паузы
  сменилась, передаётся новое значение (угол 5 и верификация идут мимо кэша). Прогон, прерванный под
  2.7.0, после обновления плагина через `resumeFromRunId` не продолжить: прежние `args` без нового
  поля скрипт отвергает, прогон начинается заново.
- **Workflow-скрипт: новый обязательный аргумент `sessionBelowOpus`** (`true`/`false`). Без него скрипт
  отказывает с сообщением: молчаливое умолчание либо отключило бы пол, либо понизило бы верификацию
  сильной сессии. Стенд — векторы 21 (слабая сессия: все уровни, повторный проход, перезапуск
  верификатора, верификация кандидатов sweep) и 22 (сильная сессия на `xhigh`/`max`), шесть проверок
  значения в векторе 6.
- **Остальные два решения пересмотра.** Канал отказа проекта от `sonnet` на повторных проходах не
  вводится (решение владельца 04.10.2026: потребитель об этом не просил). Пол модели для
  security-поверхности на `pass` ≥ 2 не решён — ждёт сравнительного прогона (`TODO.md`).

### [2.7.0] — 2026-10-04

Скилл `statusline-setup`: лимиты подписки и effort в строке статуса. Вид строки меняется.

- **Сегменты `5h NN%` и `7d NN%`** — после контекста, до ветки: сколько израсходовано лимита подписки
  в пятичасовом окне и за неделю (`rate_limits.five_hour.used_percentage`,
  `rate_limits.seven_day.used_percentage`; остаток — 100 минус значение). Пороги цвета как у контекста:
  до 59% без цвета, 60–79% жёлтый, от 80% красный. Блок `rate_limits` есть только при подписке
  claude.ai (Pro/Max) и после первого ответа API; окна нет, значение не число, отрицательное или больше
  999 — сегмент не выводится, строка цела. После времени сброса окна Claude Code убирает его из JSON —
  сегмент пропадает до следующего ответа API, а не обнуляется.
- **Effort после названия модели** — `Opus 5.5 ◔ medium` (`effort.level`, разделитель U+25D4). В
  терминал уходит только значение из строчных латинских букв длиной до 12; поля нет (модель без effort) —
  выводится одно название. Если шрифт терминала не содержит U+25D4, разделитель меняется в скрипте
  (раздел «Важно» скилла); проверка Nerd Font к нему не относится.
- **В терминал уходит только проверенное.** Из названия модели и из показываемой папки убираются
  управляющие символы (ESC, BEL, перевод строки, C1, U+2028/2029): имя каталога с
  escape-последовательностью или переводом строки больше не может переписать строку статуса. `git`
  получает путь как есть. Пустое или нестроковое название модели выводится как `?` (раньше — как есть),
  пустая или нестроковая папка и путь с NUL-байтом — как отсутствующие (берётся `cwd`, затем `.`).
- **Подпись `ctx` переименована в `Context`.** Опция tmux `@claude_ctx` и подпись `CTX` в примере для
  `~/.tmux.conf` не менялись.
- **Один вызов `jq` вместо трёх** (с новыми полями было бы шесть), JSON читается им прямо со stdin:
  поля выводятся по строке, папка — последней, за ней строка-замок, так что пустая папка и перевод
  строки в пути поля не сдвигают. На каждое поле — ровно одна строка: поле не того типа (`rate_limits`
  — строка, вход — не объект) даёт запасное значение, а не ошибку `jq`, гасившую всю строку.
  Регулярные выражения `jq` не используются — сборка `jq` без них работает. Отрицательный процент
  контекста и значение больше 999 теперь не выводятся (раньше выводились как есть); перерасход вида
  `103%` по-прежнему виден и уходит в мост tmux.
- README: строка статуса обновляется по событиям сессии, в простое — только с `refreshInterval` в
  секции `statusLine`; скилл его не ставит.
- Тест шаблона: векторы на проценты всех трёх сегментов (границы, округление, пороги цвета, значения
  и блоки не того типа), effort, управляющие символы в названии модели и в пути, выбор папки
  (`current_dir`, `cwd`, `.`), репозиторий с переводом строки в пути, вход не объект. Папка фикстур —
  свой каталог с закрытым поиском репозитория выше него: тест не зависит от того, лежит ли временный
  каталог внутри репозитория git.
- Обновление плагина установленный `~/.claude/statusline.sh` не меняет — нужен повторный запуск
  скилла.

### [2.6.0] — 2026-10-04

Скилл `statusline-setup`: мост в tmux — процент контекста в опции панели `@claude_ctx`. Совместимо.

- **Мост в tmux.** Внутри tmux шаблон `statusline.sh` кладёт процент заполнения контекста в
  пользовательскую опцию панели `@claude_ctx` (целое число, 1–3 цифры; значения нет — опция снята): сам
  tmux этого числа узнать не может, а из опции его читает строка статуса tmux. Вне tmux мост ничего не
  делает; для штатных значений вывод скрипта прежний побайтно. Обновление плагина установленный
  `~/.claude/statusline.sh` не меняет — нужен повторный запуск скилла (при `statusLine`, указывающем
  на этот скрипт, он покажет diff и спросит о перезаписи).
- **Мост не задерживает строку статуса и не пишет зря.** Вызов tmux идёт в фоне, отрезан от потоков
  скрипта и ограничен `timeout -s KILL 1`; сравнение «изменилось ли» выполняет сервер (`tmux if -F`),
  поэтому запись — только при изменении (любая запись опции перерисовывает строку статуса у всех
  клиентов tmux и перезапускает её `#(…)`-скрипты). Почему так: Claude Code отменяет скрипт строки
  статуса, не успевший до следующего обновления; клиент tmux передаёт серверу свои дескрипторы, и
  чтение его вывода ждало бы зависший сервер; клиент, застрявший на остановленном сервере с
  переполненной очередью сокета, `SIGTERM` не обрабатывает.
- **Куда пишет мост — проверяется.** `TMUX` сверяется с формой «путь сокета, pid сервера», `TMUX_PANE`
  — с `%N`; pid сервера сверяет сам сервер (`#{pid}`), так что после перезапуска tmux на том же сокете
  запись не уходит в чужую панель с тем же номером. Процент попадает в текст команды tmux только как
  1–3 цифры.
- **Требования и ограничения моста:** tmux 3.0 и новее; `timeout` с ключом `-s` (GNU coreutils,
  BusyBox от 1.30) — без них мост молча не работает, строка статуса цела. Опцию `@claude_ctx` нельзя
  задавать выше панели; Claude, запущенный из терминала редактора, открытого из панели tmux, пишет в
  панель-родителя; после выхода из Claude число остаётся в панели до следующего запуска Claude в ней.
- **Скилл знает о мосте.** Шаг 0 внутри tmux проверяет `timeout` и версию tmux (предупреждение, не
  остановка); шаг 4 сообщает об опции и показывает сегмент для `~/.tmux.conf`. Сам `~/.tmux.conf`
  скилл не меняет. Справка по чтению опции — в README: пример сегмента с проверкой значения форматом
  `#{m/r:…}`; подставлять `#{@claude_ctx}` в команду внутри `#(…)` без проверки нельзя (строка уходит
  в `sh -c`, `#{q:…}` перевод строки не экранирует, а к вложенному формату не применяется).
- **Тест шаблона** — `tests/statusline/test-statusline-template.sh`: шаблон извлекается из `SKILL.md`
  и исполняется с заглушками `tmux`/`timeout` в `PATH` (настоящий tmux не нужен). Проверяет форму
  вызова, отказ на значениях и окружении не по шаблону, неизменность вывода и то, что зависший мост
  не задерживает скрипт.
- Шаг 0: исправлено описание поведения без `jq` (скрипт завершается с ошибкой, а не выводит `?`).

### [2.5.0] — 2026-10-03

Хук напоминания после компакции и сегмент `ctx` в строке статуса. Совместимо.

- **Хук `SessionStart` (matcher `compact`).** После сжатия контекста печатает в stdout напоминание
  перечитать рабочие файлы задачи и проверить `git status`/ветку (stdout этого хука попадает в
  контекст модели). Рабочие файлы — до 3 самых свежих `PLAN-*.md`/`HANDOFF*.md` из `.dev/` и
  `.dev_files/` (без вложенных каталогов, корень проекта не просматривается) с указанием корня
  проекта; старше 14 дней и с mtime в будущем не показываются. Скрипт `hooks/post-compact-reminder.sh`
  без `jq`, всегда завершается кодом 0, нужен GNU `find` (на macOS/BSD списка нет, общий текст есть);
  тест — `hooks/tests/test-post-compact-reminder.sh`. Почему отдельный скрипт, а не `notify-sound.sh`:
  другая ответственность. Не включены: `REVIEW.md` (ревью перечитывает его само), `MEMORY.md` (Claude
  Code перечитывает после компакции вместе с `CLAUDE.md`), `doc/TODO.md` (связь — через чек-лист плана).
- **Имя рабочего файла — недоверенный ввод в контекст модели.** Пропускается только allowlist
  символов (буквы, включая кириллицу, цифры, пробел, `. _ - + , ( )`): обратная кавычка закрывала бы
  markdown-код и выводила остаток имени текстом напоминания, а C1-символы, разрывы строк Unicode,
  bidi и zero-width класс `[[:cntrl:]]` под `LC_ALL=C` не ловит. Файлы, отслеживаемые git,
  пропускаются: закоммиченный `.dev/` чужого репозитория хук не должен называть «рабочим файлом
  задачи».
- **Скилл `statusline-setup`: сегмент `ctx NN%`.** Строка статуса — `user@host:папка | модель | ctx
  NN% | ветка`; цвет: до 59% без цвета, 60–79% жёлтый, от 80% красный; до первого ответа API поля
  `context_window.used_percentage` нет — сегмент не выводится. Округление — в `jq`, не в `printf
  '%.0f'`: под `ru_RU` `printf` ждёт десятичную запятую и падает на `83.4`, а под `set -euo pipefail`
  строка не выводилась бы вовсе; нечисловое значение отсекает `numbers`, а не ошибка `jq`. Если
  `statusLine` уже настроен на `~/.claude/statusline.sh`, скилл показывает полный diff с новым
  шаблоном и спрашивает, перезаписать ли; на другую команду — спрашивает, заменить ли её (раньше
  ветка «уже настроен» не различала эти случаи).

### [2.4.1] — 2026-09-28

Скилл `review-code`: исключения skip-list записаны в одном месте, finder на `xhigh` больше не
снимает кандидата сам, формат вердикта верификатора описан явно. Совместимо.

- **Исключение из сквозного инварианта 1 — только в пункте 5 skip-list.** Раньше оно было
  записано дважды: в инварианте без условия, в пункте 5 — с условием «файл ревью не изменён в
  диффе». Оба текста уходят агентам дословно, поэтому при изменённом файле ревью указание «не
  анализировать X» одни агенты флагали, а другие гасили. Теперь инвариант ссылается на пункт 5, а
  пункт 5 прямо говорит: если scope диффа задевает файл ревью (то же условие, что в абзаце
  «Файл ревью, изменённый в ревьюируемом диффе…»), пункт, сужающий scope, в этом файле флагается
  как security-находка. «Нормы проходов» законно задают только уровень и форму scope (range правок
  или полный); исключение путей в любой секции, включая эту, — пункт, сужающий scope (добавлено и
  в таблицу секций и README). «Задевает» определено явно: путь файла ревью есть в диффе в любом
  виде, включая чистое переименование или копирование без изменённых строк. Пообъектный критерий
  «флагать только затронутый пункт» пробовали и отказались: каждая его редакция открывала новый обход (переименование файла, удаление пункта, границы
  пункта) — это часть отдельной задачи о механической защите файла ревью (`TODO.md`).
- **На `xhigh` finder не подавляет кандидата сам** (раньше так было только на `max`): кандидат
  идёт в обычный список с пометкой `skip_note` «под skip-list: …» (поле добавлено в «Формат
  кандидата»), а запись, всё же вернувшуюся в `suppressed`, сессия или скрипт переводят туда же
  (на `medium`/`high` — только запись с признаком security).
  Снять такого кандидата может только голос `SUPPRESSED` верификатора. Почему: `xhigh` — пол
  `todo-ship` и зон ядра, и одного голоса finder'а без проверки там мало. Цена: на `xhigh` больше
  кандидатов доходит до верификации — больше верификаторов, а сверх потолка кандидатов угла
  подавленное уходит в `overflow` и прогон становится `деградированный`. В скрипте набор уровней —
  величина-зеркало `NO_SELF_SUPPRESS`.
- **Формат вердикта верификатора описан в фазе 2**: `id`, `verdict`, `evidence`, `security`, а в
  режиме `Workflow` — ещё `duplicate_of`. Правило пункта 4 «security-находка — если так отнёс хотя
  бы один голос» опиралось на поле `security` у верификатора, но в режиме `Agent` верификатору не
  было сказано его возвращать. Формат входит в `verifyProtocol`. Пункт 4 теперь считает голосом
  любого верификатора, а не только линзу `max`, и голос без признака `security` — «да»
  (fail-closed).
- **Стенд workflow-скрипта:** векторы 15–20 — самоподавление на `xhigh` (от углов и от sweep),
  security-запись на `high` с сохранением признака, security-голос одиночного верификатора и одной
  линзы `max`, `medium` без подъёма. Каждый проверен мутацией: мутант кода роняет свой вектор.

### [2.4.0] — 2026-09-28

Новый скилл `debug` — систематическая отладка: сначала корневая причина, потом одна проверенная
правка. Совместимо.

- **Новое: `skills/debug`.** Четыре фазы: причина (ошибка и стек целиком, воспроизведение,
  изменения от рабочего состояния, `git bisect` — только при чистом дереве и с `git bisect reset`, в
  системе из нескольких звеньев — временное логирование на каждой границе, трассировка значения к
  источнику) → сравнение с работающим аналогом → одна явная гипотеза и минимальная проверка (эксперимент
  откатывается всегда) → исправление. Почему: типовой сбой агента на баге — серия догадок, где каждая
  заплатка чинит симптом и ложится поверх предыдущей.
- **Исправление — с тестом, увиденным красным до правки;** тест, написанный после правки, —
  отступление, которое проверяется мутацией и называется в отчёте. Перед правкой — базовый прогон
  набора, после — весь набор с падениями по именам против базовой линии; что не прогнано — говорится
  прямо. Флаки — многократные прогоны. Неудачная правка откатывается до следующей.
- **Три неудачные правки — стоп:** дерево приводится в порядок, доклад — проверенное, итоги трёх
  правок и варианты (новая гипотеза, смена подхода, пересмотр архитектуры участка). Выход к

### [2.3.1] — 2026-09-28

Хук `guard-bash`: текст сообщения коммита или PR больше не проверяется как команды (строгие
шаблоны), правило `.env` находит обращения точнее, закрыты обходы через glob, кавычки, редиректы и
опции git. Совместимо.

- **Шаблоны сообщений — единственный источник исключений «текст, а не команда».** Команда-сообщение
  (`git commit … -m "…"`/`-F -`, `gh pr|issue create|edit|comment|merge … --title/--body "…"`/
  `--body-file -`, с here-doc `<<'EOF'` или `-m "$(cat <<'EOF' …)"`, одиночный `echo`/`printf`)
  ищется по строгой грамматике, в том числе внутри цепочки (`cd x && git add … && git commit …
  && git push`). Её текст заменяется меткой, тело here-doc отбрасывается; команды до и после,
  пути, флаги и цели редиректов проверяются всеми правилами как обычно. Почему: прежняя нарезка
  считала каждую строку тела here-doc командой, и сообщение со словами `.env`, `rm -rf`,
  `git push --force` или `printenv` блокировалось.
- **Почему не общий разбор bash.** Первая версия правки решала «данные или код» лексером по
  грамматике bash; два прохода ревью нашли десять расхождений лексера с bash (`${x:-<<EOF}`, `<<<`
  в `$( )`, `$'EOF'`, `#` в `$( )`, CRLF, `EOF)`, `$(` после разделителя, конвейер в теле, `2>` как
  вывод в файл, `coproc`), и каждое прятало настоящие команды за «данными». Шаблон мал и проверен
  целиком: текст сообщения — без `$`/`` ` ``/`\`, флаги — из короткого списка, `-c` у git — только
  `user.name`/`user.email`, конвейер после команды-сообщения — не шаблон. Цена: вне шаблона
  (`cat <<'EOF' > notes.md`, `(echo …)`, слитное `git commit -am.env`) упоминание `.env` по-прежнему
  блокируется — такой текст пишется через Write и `-F`/`--body-file`.
- **Правило `.env` по токенам лексера** (кавычки, `$'…'`, комментарии, подстановки; исключений
  лексер не даёт). Закрыты обходы, часть из которых была и в 2.3.0:
  - glob и кавычки: `cat .env*`, `.env{,}`, `.env~`, `.e""nv`, `.\env`, `$'.env'`, `$'\x2eenv'`,
    `{x,.env}`, `open(f'.env')`;
  - присваивание и опции: `f=.env; cat $f`, `curl -F f=@.env`, слитное `-F.env`;
  - редирект и allowlist: `ls > .env`, `> .env ls`, `git check-ignore --stdin < .env`,
    `git -c core.fsmonitor=… status`;
  - подстановки: `ls $(cat .env)`, `ls <(cat .env)`, `$\⏎(`.

  Кавычки и `\` снимаются по правилам bash (`grep "\.env"` — регулярка, не путь; «боевой .env.» —
  точка в конце фразы). Неполный glob (`.en?`) и путь через переменную или файл-посредник текстом
  не различимы — принятое ограничение, его закрывает sandbox ОС.
- **Fail-closed при сбое:** `trap EXIT` превращает любой код, кроме 0 и 2, в блокировку (команда с
  хвостовым `\` роняла разбор с кодом 1, который Claude Code считает неблокирующей ошибкой);
  `command` не строкой (массив) — блок, а не пропуск. `printf … | grep -q` заменены на here-string:
  под `pipefail` ранний выход `grep -q` давал SIGPIPE, и условие становилось ложным (в том числе у
  правил секретов). Правила `git reset --hard`/`push --force`/`branch -D`/`/proc/*/environ`
  смотрят очищенную шаблоном команду — упоминание в тексте коммита их больше не срабатывает.
- **Скорость.** Разбор по байтам (`LC_ALL=C`) кусками через `sed` + `mapfile`, без квадратичных
  проходов (подстрока `${s:i:1}` в bash — O(длины строки), и на ~400 КБ хук выходил за таймаут
  600 с, при котором хук команду не блокирует). Команда длиннее 32 КБ лексером не разбирается —
  `.env` ищется грубо. Шаблон сообщений — только в командах до 16 КБ и не более 8 вызовов на
  команду: без потолка рекурсия по цепочке из сотен `git commit -m "x" &&` была кубической (632

- **В тексте блокировки — готовые обходы:** текст с `.env` — в файл и `-F`/`--body-file`; проверка
  `.gitignore` — `git check-ignore -q .env`.
- Тест-векторы: 347 ассертов (+188): воспроизведения всех подтверждённых обходов трёх проходов
