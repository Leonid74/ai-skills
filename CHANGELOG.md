# Changelog

Формат основан на [Keep a Changelog](https://keepachangelog.com/ru/1.1.0/). Версии — отдельно по
каждому плагину маркетплейса (своя версия в `plugins/<plugin>/.claude-plugin/plugin.json`), плюс
отдельный раздел для изменений самого репозитория-маркетплейса, у которого нет собственной версии.

## dev-toolkit

### [2.3.0] — 2026-09-26

Новый скилл `server-disk-cleanup` — анализ и согласованная очистка места на диске Linux-сервера.
Совместимо.

- **Новое: `skills/server-disk-cleanup`.** Фазы: предусловия (`findmnt`, `df -i`, `sudo -n`) →
  разведка только чтением (`du -x` с `timeout`, Docker, журнал, apt, старые ядра, кеши, каталоги
  сессий Claude Code, удалённые-но-открытые файлы) → проверка «не используется ли» → таблица А/Б со
  сквозной нумерацией → выполнение → замер `df` до/после и сверка томов/контейнеров. Почему: процедура
  отработана вручную на staging-VPS (33 → 26 ГБ), где `docker image prune -a` удалил бы базовые
  образы деплоя, а полный `builder prune` — кеш автодеплоя.
- **Согласие на удаление — только номера в ответе на прямой вопрос.** Исходная просьба («почисти»,
  «освободи место») запускает лишь анализ; на ответ без номеров вопрос повторяется, и модель не
  предлагает свой перечень на подтверждение «да»; согласие не переходит на пункт, изменившийся при
  повторной проверке перед выполнением.
- **Своя политика удаления, не зависящая от хука `guard-bash`:** только адресные команды (без
  `prune -a`/`volume prune`; `builder prune` — с `-f` и `--filter until=168h`), кеши — командами
  менеджеров; в команды подставляются только пути из безопасного набора символов (иначе —
  «неопознанное»: имя каталога бывает чужими данными); рекурсивное удаление внутри `/tmp` — только
  своих объектов, без `sudo`, по одному пути без масок; вне `/tmp` — командой пользователю (через
  `! …`, а с `sudo` при пароле — в отдельном терминале: в режиме `!` sudo не спрашивает пароль и
  молча завершается); живой лог — `truncate`, не `rm`; проверка пути `realpath`/не symlink/не
  `/`/`$HOME`/не точка монтирования. Почему: у пользователя маркетплейса хука может не быть, а маска
  в `rm` проходит текстовую проверку хука и раскрывается уже при исполнении.
- **Проверки «не используется ли» — fail-closed:** пустой вывод `lsof +D`/`find` считается
  доказательством только при нужном коде возврата (таймаут, нет прав, нет утилиты — «не удалось
  проверить», объект не предлагается); тома — по `docker ps -a --filter volume=` (поле `Mounts` без
  `--no-trunc` обрезано), любой том — группа Б; «свежесть» образа — по `LastTagTime` (время pull), а не
  `CreatedSince` (время сборки); живые сессии Claude Code — по открытому процессом `claude` каталогу
  `<сессия>/tasks`.
- **Замеры — файлами в рабочем каталоге сессии:** `df` и `df -i` «до/после» (плюс `df /` — в
  контейнере корень бывает `overlay`), снимок томов/контейнеров/сервисов; переживают сжатие контекста.
  `du -d` вместо GNU-only `--max-depth` (BusyBox), код возврата `du` проверяется (таймаут — вывод
  неполный); снапшоты btrfs/zfs — в «найденные проблемы».
- **Секреты на разведке:** `docker inspect` только с `--format`; процессы — только имя и PID (не
  `pgrep -a`); crontab — только расписание и путь команды (фильтр `awk` скрывает значения переменных и
  аргументы), скрипты бэкапов — адресным `grep`.
- **Справочник `references/caches.md`:** dnf/yum, snap, flatpak, journald, podman, логи контейнеров,
  npm/yarn/pnpm, pip/uv, composer, go, cargo, gh, Claude Code и список «установлено, не кеш»
  (тулчейны, версии рантаймов, браузеры Playwright — удалять только менеджером).
- Приёмы заимствованы из разбора аналогов на GitHub (`inline-chat/inline`, `glebis/claude-skills`,
  `hm-docker-clean`, `domdoss/Warden`, `colonelpanic8/dotfiles`, `docker-gc`, `kondo`); их
  `system prune -a --volumes` и очистка «безопасного» без вопроса осознанно не перенесены.
- **`optimize-project-docs`:** из триггеров убраны «почисти память проекта», «почисти CLAUDE.md» и
  `clean up` — они пересекались с очисткой диска; в `Skip for` добавлена `server-disk-cleanup`.

### [2.2.0] — 2026-09-23

Хук `guard-bash`: правила секретов ловят значения секретов и чтение секретных файлов/окружения, а
не слова. Совместимо: ложных блокировок меньше, реальных утечек ловится больше.

- **Удалено правило «слово `secret`/`password`/`token` в любом месте команды».** Почему: оно
  блокировало имена классов, путей и тестов (`--filter=…TokenTest`, `VerifyApplicationToken.php`,
  `echo "tokens used"`), из-за чего в проектах-потребителях появились обходы «через файл», и при
  этом не ловило ни одного реального ключа (`Bearer ghp_…`, токен Telegram-бота в URL).
- **Новое: значения известных форматов** — GitHub (`ghp_`/`gho_`/`ghu_`/`ghs_`/`ghr_`,
  `github_pat_`), Anthropic `sk-ant-`, OpenAI-подобные `sk-`, Slack `xox?-`, AWS `AKIA`/`ASIA`,
  токен Telegram-бота, JWT, PEM `PRIVATE KEY`. Блокировка без эхо команды.
- **Новое: присваивание литерала** ≥ 8 ASCII-символов имени `password`/`passwd`/`secret`/`token`/
  `api_key` (`--password=…`, `API_KEY: …`, JSON `"token": "…"`, PHP `'password' => '…'`,
  `?token=…` в URL). Ссылка на переменную (`$VAR`) и путь к файлу (`TOKEN_FILE=/run/…`)
  пропускаются; оператор `::` (`Password::defaults`, `--filter=…TokenTest::test_x`) и русский текст
  после `token:` в сообщении коммита литералом не считаются. Сообщение блокировки подсказывает обход:
  секрет — через переменную окружения или файл.
- **Новое: вывод окружения** — голые `printenv`/`env`/`export`/`set`/`declare`/`typeset` (допустимы только флаги),
  `docker compose config`/`docker-compose config`, `docker`/`podman`/`kubectl … exec … env`,
  `/proc/*/environ`. `env FOO=1 cmd`, `set -euo pipefail`, `printenv HOME` пропускаются. Docker-
  правила сверяются по токенам от команды сегмента, поэтому `grep … docker-compose.yml config/…` не
  блокируется.
- **Правило `.env` стало fail-closed** (решение владельца): сегмент команды с путём `.env` или
  `.env.<суффикс>` блокируется при любой команде, кроме `ls`/`stat`/`test`/`[`/`[[`/`git status`/
  `git check-ignore`. Прежний список «читающих» утилит (`cat`/`less`/`head`…) пропускал
  `grep`/`sed`/`awk`/`source`/интерпретаторы/`cp`. Шаблоны `.env.example`/`.env.dist`/`.env.sample`
  теперь разрешены любой командой (раньше `cat .env.example` блокировался). Цена fail-closed:
  `cp .env.example .env` и упоминание `.env` в тексте команды (например, в сообщении коммита)
  тоже блокируются — обход через файл.
- Тест-векторы: +115 ассертов (таблица задания, позитив/негатив по каждому формату и правилу).
  Каждый проверен мутацией; `GUARD_BASH_HOOK` подменяет проверяемую копию хука.
- Сверка на 14 433 реальных Bash-командах из транскриптов проекта-потребителя: 500 прежних ложных
  блокировок снято; новые блокировки — чтение/копирование `.env` и `env | grep`, а также
  упоминание `.env` в heredoc и заголовке PR (цена fail-closed).

### [2.1.0] — 2026-09-22

`review-code`: бриф агентов не дублирует то, что среда загружает им сама (пункт `TODO.md`).

- **Правила из автозагружаемых файлов (корневой `CLAUDE.md`, его `@`-импорты) — ссылками, а не
  текстом.** Почему: замер транскриптов 53 агентов в проекте-потребителе (прогон `xhigh` и два
  workflow-прогона) показал, что корневой и глобальный `CLAUDE.md` и `MEMORY.md` автозагружаются в
  каждого субагента в обоих режимах, а общий кэш между агентами — только системный промпт и схемы
  инструментов (~16,7 тыс. из ~74 тыс. стартовых единиц контекста). Строка `context` входа
  workflow-скрипта требовала «правила проекта дословно с путями» — при буквальном исполнении каждый
  агент оплачивал вторую копию того, что у него уже есть. Ссылка допустима, только если файл
  автозагрузкой получила и сама сессия; раздела нет — агент дочитывает файл через `Read` по
  абсолютному пути.
- **Дословно — только то, чего у агента нет:** секции файла ревью, вложенные `CLAUDE.md`
  затронутых каталогов и правила skip-list (их цитируют finder и верификатор — нужна ровно та
  редакция, что извлекла сессия, из какого бы файла она ни была).
- **Изменённый в диффе файл правил — предупреждение, а не «редакция базы» в брифе.** Пункт TODO
  предлагал передавать агентам изменённые места `CLAUDE.md` в редакции базы. Ревью ветки показало,
  что форма брифа защиты не даёт: автозагрузку не отменить, а фаза 0 извлекает skip-list и уровни
  из той же новой редакции. Решение владельца — не обещать защиту, которой нет: правка файла правил
  (определение по свойству — фаза 0, п. 3 `SKILL.md`; обнаружение неполное) называется в заголовке
  вывода и в «заметках» сводки (они доходят до описания PR) для ручной проверки. Механическая
  защита — фаза 0 не
  применяет правила, добавленные `+`-строками диффа, как у файла ревью, — остаётся пунктом
  `TODO.md` (б).
- Формат входа workflow-скрипта не менялся — меняется только то, что скилл кладёт в `context`.

### [2.0.0] — 2026-09-20

Задача C2 плана «Конвейер ревью v3» проекта-потребителя (п. 10): конвейер `review-code` оформлен
workflow-скриптом. Мажорная версия — меняется механика оркестрации и темп запуска агентов; состав
углов, модель субагентов, протоколы верификации, skip-list, инварианты и потолки находок не менялись.

- **Workflow-скрипт `workflows/review-code.js`** (`dev-toolkit:review-code-pipeline`): фазы «Поиск»,
  «Верификация» (на `max` — три линзы на группу локаций), «Sweep», «Сводка». Почему: в режиме `Agent`
  каждый ответ агента оседает в контексте сессии, а группировку и подсчёт голосов сессия ведёт «в
  уме»; в скрипте результаты остаются в переменных, голоса (`≥2` конструктивных `REFUTED` на `max`,
  раздельный счёт `SUPPRESSED`, security-исключение) и модель по роли и проходу считаются кодом,
  прерванный прогон возобновляется (`resumeFromRunId`) с кэшем завершившихся агентов. Тексты правил
  в скрипте не дублируются — скилл передаёт их через `args` из своего `SKILL.md`.
- **Темп запуска — волны по 5** (оба режима; решение владельца после ревью этой же ветки: залп из 20
  линз целиком сгорел об лимит сессии без единого сохранённого ответа). Волна → дождаться всех →
  журнал ответов → перезапуск отказавших → следующая волна; первыми — security и корректность.
  **Лимит использования — не отказ агента**: HTTP 429, исчерпанный бюджет хода либо волна без
  единого ответа останавливают запуск без траты перезапуска, угол отказавшим не помечается, прогон
  продолжается с недостающих (в `Workflow` — через resume), иначе возвращается как `прерван` с
  перечнем несделанного (`pending`). Лимит распознаётся по целым словам сообщения (обычная ошибка
  агента со словом `generate` или `delimiter` прогон не останавливает); сгоревшие об лимит запуски
  считаются отдельно (`limitHits`) и в число агентов не входят; волна меньше двух не допускается —
  на ней распознавание тихого лимита не работает. Проверено на деле: при ревью этой ветки лимит
  выбил волну из пяти верификаторов — углы (≈0,7 млн токенов) повторять не пришлось.
  Верификация `pipeline`'ом заменена волнами заданий «группа × линза».
- Skill `review-code` — раздел **«Оркестрация фаз 1–2.5»**. Режим `Workflow` — только при трёх
  условиях: инструмент доступен; скилл вызвал пользователь **slash-командой** либо прямо попросил
  workflow (просьба о ревью обычными словами и автономный вызов основанием не являются — у
  `Workflow` обязательный opt-in, самосогласие не допускается); оценка числа агентов (`medium` — 7,
  `high` — 11, `xhigh` — 22, `max` — 46; считается по группам верификации, а не по углам)
  укладывается в ориентир «Dynamic workflow size». Оценка выше ориентира — остановка с выбором;
  спросить некого — режим `Agent`. Число агентов, на которое есть согласие, уходит в скрипт
  (`maxAgents`) — он укрупняет под него группы верификации, а любое превышение (углы и sweep
  запускаются всегда) называет сам: нота и `agents.overMax`. На `xhigh`/`max` заголовок называет
  оценку числа агентов и расхода. Прежний режим `Agent` **сохранён как фолбэк**. `Workflow` в
  `allowed-tools` намеренно не добавлен: диалог разрешения остаётся гейтом (как `Write` в 1.17.0).
  Фолбэк `scriptPath` — только абсолютный путь внутри каталога плагина, никогда не от рабочего
  каталога ревьюируемого проекта.
- **Защиты, выраженные кодом скрипта** (находки ревью `max` этой ветки): подавление finder'ом не
  принимается на веру на `max` и для security-записей — такой кандидат идёт на верификацию; тексты
  кандидатов передаются верификаторам и sweep JSON-блоком с пометкой «данные», противоречивые
  вердикты по одному `id` не засчитываются; путь кандидата вне репозитория отклоняется без
  верификации и не попадает в промпты (как и всё, что не похоже на путь: переводы строк, `~`, схема
  URL, чрезмерная длина), неоднозначный суффикс разрешается по самому длинному совпадению, путь
  кандидата в текст задания верификатору не подставляется; security-признак для skip-list — флаг
  **или** категория из щедрого перечня корней, но на срез он не влияет: срез сверх потолка идёт в
  порядке возврата (иначе содержимое диффа управляло бы тем, что дойдёт до верификации), срезанное
  целиком возвращается в `overflow` и делает прогон `деградированный`, а поднятое из `suppressed`
  потолок кандидатов не делит; номер угла обязан быть числом (строковый `"5"` уводил security-угол на модель
  дешёвой роли); при неполном составе линз пороги снятия не смягчаются, а `CONFIRMED` требует двух
  голосов; дубли по механизму помечает верификатор (`duplicate_of`); sweep видит снятое
  верификацией, а его кандидат на уже судившейся локации помечается.
- Сводка прогона: новые поля **«оркестрация»** (`Workflow` с run-id / `Agent` с причиной / оба
  отрезка / `нет (без агентов)`) и **«заметки»** (ноты, отклонённые пути, дубли); режим `прерван`;
  перезапуски — **по ролям** (раньше любой перезапуск назывался «перезапуском упавшего угла»); поле
  **«токены»** в режиме `Workflow` — общая сумма из `usage.subagent_tokens` уведомления о завершении
  workflow (при resume — сумма запусков), разбивки по моделям нет — скрипту расход не виден.
  `cppr` и `todo-ship` переносят поле «оркестрация» целиком.
- «Формат кандидата» дополнен полями `category` и `security` (их требует схема скрипта; от `security`
  зависит пункт 4 skip-list). **Отказ sweep-finder'а описан** (закрыт пункт `TODO.md` от 20.09): один
  перезапуск, второй отказ — `деградированный` «sweep не отработал». Второй отказ угла в режиме
  `Workflow`: вариант «перезапустить угол без `model`» исполняется режимом `Agent`.
- Стенд-заглушка `tests/workflows/test-review-code.mjs` — 14 сценариев: все четыре уровня, модель по
  роли и проходу, порядок запуска по ценности, волны (потолок одновременности **и** барьер
  «дождаться всей волны» — мутант со скользящим окном сценарий не проходит),
  лимит против отказа агента, линзы и skip-list, подавление finder'ом, срез по потолку, пути
  кандидатов, текст кандидата как данные, дубли по механизму, потолок агентов, сообщения проверки
  `args`, ловушки артефакта (детерминированные промпты, запрещённые вызовы, литерал `meta`). Оба
  JS-файла — в формате Prettier с дефолтами.
- Известное принятое ограничение: агенты workflow — `general-purpose` с Bash; при диффе больше ~300
  строк они сами выполняют предписанную read-only команду, и от опасных подфлагов их удерживает
  только текст инварианта 3 (в проектах без хука `guard-bash` механического барьера нет).

### [1.21.0] — 2026-09-20

Решения владельца по находкам ревью C1 (PR #48), вынесенным ему: правило «Модель субагентов»
остаётся как есть, но его цена перестаёт быть молчаливой.

- Skill `review-code` — **уведомления о модели** в блоке заголовка вывода (и повтором в поле
  «прогон» сводки): на `pass` ≥ 2 — что finder-углы и sweep идут на `sonnet`, на `max` — что это
  включает поиск по security-поверхности и контрактам (пола модели нет); что проект не может
  отменить `sonnet` на повторных проходах, если в его правилах есть текст о модели (темы «модель» в
  правилах ревью нет); что при сессии слабее `opus` (либо неизвестной) верификация может пойти на
  модели слабее finder'ов.

    коротких флагов (`-cw`);

    останавливается на `--` (дальше — пути), scope осознанно ограничен ровно auto-approved
    префиксами `allowed-tools` скилла review-code — глобальная блокировка `gh … -R`/`--web` ломала

    безопасность / воспроизводимость); выжившее выводится одним вызовом `ReportFindings`;
  - правила ревью вычитываются из `CLAUDE.md` целевого проекта; при их отсутствии применяется
    дефолтная эвристика с явным сообщением об этом;
  - обрабатывается ловушка пустого scope после пуша: сообщение «scope пуст» вместо ложного
    «находок нет»;
  - облачный `ultra` вне цели: скилл может только предложить пользователю набрать `/code-review ultra`.
- Почему skill, а не команда: с версии CLI 2.1.215 встроенный `/code-review` помечен
  `disable-model-invocation` — модель не может вызвать его сама, из-за чего проектные флоу с
  обязательным шагом «ревью диффа» не выполнялись автономно.
- **Переименование (ломающее для пользователей):** slash-команда `/dev-toolkit:review` →
  **`/dev-toolkit:review-quick`** (файл `commands/review.md` → `commands/review-quick.md`).
  Имена теперь отражают функцию: `review-quick` — быстрый однопроходный обзор,
  `review-code` — многоуровневый пайплайн, `review-last` — обзор последнего коммита.
  Старое имя `/dev-toolkit:review` больше не работает — поправить в проектных флоу и `CLAUDE.md`,
  где оно упоминается.
- `plugin.json`: `description` дополнен упоминанием многоуровневого ревью.
